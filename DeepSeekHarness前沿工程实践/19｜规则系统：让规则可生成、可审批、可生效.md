### Agent 怎样把意图翻译成规则：给定意图、受约束生成

```
这一讲我们换个主角：让 Agent 来写。你只给它一句话：“阻止所有访问 /admin 的探测请
```

求”，它就回你一条规则：

```json
{
 "name": "block admin probe",
 "when": { "field": "path", "op": "starts_with", "value": "/admin" },
 "action": "deny"
}
这条规则和第 18 讲你手写的规则是同一套结构，name/when/action 都在。区别只在写的
```

人从你换成了模型：它读取你那句自然语言的意图，然后把它翻译成结构化规则。

```
模型不是凭空知道这套结构的。起草的 prompt 里写明了字段约定（见 agent-draft.ts 的
SYSTEM）：字段有哪些、field 与 op 各能取哪些值。但那只是告知，模型可能不会照办，
```

比如拼错字段名、漏字段、自创算子，所以还要“受约束生成”。真正把关的是代码校验，它用


在安全边界里填空，吐出来的规则一定合法，不合法的当场被拒。

### 人怎样掌握变更的决定权：审批闸、自主级别与 /firewall 命令

这条候选能直接上线吗？本讲最关键的一条产品决定是：人始终在 Agent 之上。Agent 能起草、能建议，但中间隔着一道闸，开多大由人说了算，自主级别是人设的，Agent 自己提不了级。

落到机制上，有三样东西：

1. 审批闸，装在流水线前两站，一道按级别拦写操作、一道用白名单限定工具范围；

2. 自主级别，决定这道闸开多大；

```
/firewall 命令，它是人自己动手的入口。
```

前两样合起来就是那道闸，它拦的是 Agent；命令是人手动操作规则系统的入口，不受闸的限制。

先说审批闸。Agent 每次调工具都要穿过 dsh 的工具流水线，第 06 讲说过，那条流水线有八道关，其中前两站决定“这一次到底执不执行”。本讲的审批闸就装在这两站上，负责装它的

```bash
函数是 mountApproval：
export function mountApproval(ctx: Context, level: () => AutonomyLevel): void {
 // 挂在 tools/pre-execute 上：先让后续策略跑完，再按级别决定要不要拒绝
 ctx.on('tools/pre-execute', async (exec, next) => {
   const decision = await next()
   const reason = denyReasonFor(level(), exec.name)  // 写操作在低级别下被拦
   if (reason) return { kind: 'deny', reason } as typeof decision
   return decision
 })
 // 单调守卫：只做"工具在不在白名单里"这一个判断
 ctx.tools.guard((exec) => guardReasonFor(exec.name))
}
```

它不是 Agent 能调用的工具，而是把监听器与守卫注册到流水线上的函数，注册写法见第 06讲。注册的两段判断的都是“Agent 这次工具调用该不该放行”：

```
前一段挂在 tools/pre-execute 上：这一站是策略层，能放行、拒绝或转审批；本讲只
取“拒绝”，按级别直接 deny，不走 ask，那会把决定权转给审批服务；因为要不要人点头
```

- 是事先定好的，不必临时去问；具体怎么定，下面讲。

```
后一段是白名单守卫（ctx.tools.guard）：约束层，只能拒绝或弃权。它按工具名判
```

- 定，不在白名单里的工具一律拒绝，它只列允许的，没列进来的默认不放（fail-closed）。

```

```

```

```

```

```

- 用的。这是第 18 讲的默认模式，也是多数部署的样子。真切成白名单模式，默认拒绝、命

```
三个动作按效果说：起草是提议一条新规则（firewall_draft），只是新增一条不生效的候
```

### 批准后的规则怎样实际生效：从账本到生效

如果我们批准了一条规则，它怎么变成实际生效的规则？

```
先把两侧分清楚：控制面改规则、下命令，上一节的 /firewall 命令与审批闸都在这一侧；
```

数据面真正拦截请求。上一节讲的是控制面怎么把关；这一节讲剩下的一步：变更记下来之后，数据面怎么读到新规则，让它真的生效。

最直接的做法是改规则文件，但那不行：改了什么无从追溯、不可审计，两个变更同时改还会互相覆盖。所以本讲用 ledger（账本） 串起整条链路，名字借自会计的账簿：每笔变更记一条流水，当前的规则集由流水累加得出；你不能直接改这个“余额”，只能往后面追加流水。落到技术上，每一条流水就是一条事件，它不另写一个自己管的文件，而是以插件注入的

```
user/message 作为载体，来源标注成 plugin:firewall-ledger，追加进 dsh 的会话
```

日志，也就是第 08 讲那份只追加的日志；而那个“余额”就是规则文件，它只是这串事件当

```
前折叠（fold）出来的产物，随时能由账本重建。
```

具体来说，规则要真正生效，得走三步：变更记成事件，这些事件折叠出规则集，再落成数据面读的文件。

先说账本。账本就是那串事件本身，每一次变更落一条，只往后追加，不改已经记下的。这是

```
Agent 起草落的那条：新增一条规则，state 是 candidate，刚生成，还不生效。
{
 "type": "rule.add",
 "id": "rule-7a9546c1",
 "state": "candidate",
 "at": 1750000000000,
 "by": "Agent（firewall_draft）",
 "input": {
   "name": "block ip 1.2.3.4",
   "when": { "field": "ip", "op": "eq", "value": "1.2.3.4" },
   "action": "deny"
 }
}
```

```
这是人批准落的那条：patch 是空的，因为批准只把状态从 candidate 改成 active，不
```

动规则内容。

```sql
{
 "type": "rule.update",
 "id": "rule-7a9546c1",
 "state": "active",
 "at": 1750000000001,
 "by": "人（/firewall approve）",
 "patch": {}
}
两条都带 by 与 at，标注这次变更来自谁、发生在什么时候。by 的来源有三类：人的命令、
```

Agent 的工具，以及人绕过账本直接改文件的带外修改。少了这两个字段，事后就分不出“这条规则是 Agent 在级别 2 下自己转正的还是人批的”，也说不清几笔改动的先后；有了它们，逐条读事件就能复原一次规则变更的经过，这正是“人掌握决定权”能被审计的关键。

```sql
上面两条分属其中两类。本讲一共四类事件：rule.add 新增、rule.update 修改、
rule.reject 驳回或下线、rule.remove 删除。
```

再说折叠：拿一个初始状态，把事件按顺序逐个作用上去，走完得到最终状态。本讲是从一个空 Map 出发，事件依次作用，最后剩下什么规则，就是当前规则集。实现就是一个 Map 从头走到尾：

```sql
export function fold(events: RuleEvent[]): Rule[] {
 const map = new Map<string, rule>()
 for (const e of events) {
   if (e.type === 'rule.add') {
     map.set(e.id, { ...e.input, id: e.id, state: e.state ?? 'candidate' })  //
   } else if (e.type === 'rule.update') {
     const r = map.get(e.id)
     if (r) map.set(e.id, { ...r, ...e.patch, state: e.state ?? r.state })
   } else if (e.type === 'rule.reject') {
     const r = map.get(e.id)
     if (r) map.set(e.id, { ...r, state: 'rejected' })  // 驳回不是删除，是标 rejec
   } else {
     map.delete(e.id)  // rule.remove
   }
 }
 return [...map.values()]
}</string, rule>
```

### 本讲小结

这一讲把规则从“纯手工操作”推进到“可生成、可审批、可生效”。

```
受约束生成：模型按 prompt 写明的字段约定起草，代码侧 isValidRuleWhen 把关，
field / op 只能取约定值、value 非空，吐出的规则一定合法；第一稿一律是候选，不直
```

- 接生效。

```sql
审批闸与自主级别：审批闸装在工具流水线前两站，tools/pre-execute 按级别拦写操
作、tools.guard 用白名单限工具范围；自主级别分为三档：0 / manual / off、1（默
认）、2，决定闸开多大，人用 /firewall 命令来掌控。
账本：变更记成 rule.add、rule.update、rule.reject、rule.remove 四类事
```

- 件，追加进会话日志，折叠出规则集再原子写落成数据面读的文件，文件只是产物，权威在会话日志。
