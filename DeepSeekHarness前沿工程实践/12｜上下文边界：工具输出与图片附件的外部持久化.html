12 | 上下文边界：工具输出与图片附件的外部持久化 ​

你好，我是张嘉熙。

核心篇讲到这里，能力、工具和会话都齐了——只差最后一条边界没划：模型眼前那份上下文，到底该装什么、又该把什么留在外面？

其中最占地方的是两类：工具吐出的大段输出、用户拖进来的图片。装不下之后怎么腾地方，第 10 讲我们聊过了，本讲看的则是更前面一步——该不该让它们直接整份进去：

  • 工具一次吐出一大段文本，该整份进上下文吗？

  • 用户拖进来的一张截图，也该整份进上下文吗？

这两类，dsh 给它们各开了一条外置通道——下面两节各讲一条。

关于环境：本讲新增三个包——@deepseek-ai/dsh-attachment-local（附件的本地
后端）、@deepseek-ai/dsh-home-paths（它的 peer 依赖），以及 @deepseek-
ai/dsh-output-retention（策略插件裁头尾预览要用），已加入本项目的
package.json，npm install --legacy-peer-deps 装上即可。溢出存储的三个包
（@deepseek-ai/dsh-spill / -local / -policy）此前只写在依赖里，本讲才第一
  • 次真正用上。
两点提醒：本项目用 --legacy-peer-deps 安装，peer 依赖必须显式写进
package.json，漏了就报 ERR_MODULE_NOT_FOUND；附件后端还要用到原生模块
sharp（装的是预编译包，不用本地编译）。
关于示例：npm run start:ch12:spill 跑溢出存储（超大的工具输出怎么被换成预览
和指引），npm run start:ch12:attachment 跑图片附件（存进去、看字节落在哪、
看日志里留下什么、再取回字节），npm run start:ch12:admission 跑准入（超限和
  • 不合规怎么被拒）。

工具输出的外部持久化：溢出存储 ​

第一个问题：工具一次吐出一大段文本，该整份进上下文吗？

不该。这样一大段输出不该原样整段进下一次请求（官方原话是不应完整占用下一次模型请求），但它后面可能还有用。另外，日志只追加、不改写（第 8 讲），一旦写进去就再也删不掉了。

那这些内容放到哪儿？存成文件，日志里只留预览和指引，这就是溢出存储（spill），分两步：完整存成文件，然后让进日志的那份只留“头尾预览 + 一句去哪儿读全文”。

两个“溢出”要分清，它们只是同名，不是一回事：本讲的“溢出存储”是当场定的，工具一跑

完，在写进日志之前判定单条输出的字节数（跟部署配的 maxInlineBytes 比）；第 10

讲的“溢出”是请求被拒之后才确认的，判断的是整个请求超没超模型的窗口。

落到实现上，动手的是溢出策略插件 dsh-spill-policy——它本质是个结果转换器：工具

跑出来的结果，超了阈值的就被它换掉，原文一份不丢。它注册两个监听器，挂在两处：一是

工具执行之后（tools/post-execute），结果超了阈值就整份存走；二是 Code Mode（
第 6 讲）的 tools/code-dispatch-log：Code Mode 里，run_code 程序会调别的工
具，每个结果程序先拿去继续跑，还会再记一份进日志留档（tool/code-dispatch 事

件）。策略插件管的就是日志这份：超了阈值，就换成预览加指引（原文已另存成文件）。

这个插件只提供一个配置项 maxInlineBytes，两个监听器都照它判。判据也就一句话：超

过这个字节数就存成文件，不超过就照原样进上下文。它没有内置默认值，阈值是部署决策，库不替你定；不配，就什么都不发生，工具输出照旧整份进上下文。

名字分清楚了，还有一处更容易混：溢出存储跟第 10 讲的压缩、裁剪都在对付“装不下”的问题，但管的不是同一件事。先把它们摆开：第 10 讲对应的是裁剪，它和溢出存储一样，管的都是单条过大；压缩管的则是“历史整体太长”。而压缩、裁剪都是事后在 surface 上动手、只往后追加、不改已有事件，溢出存储却在写进日志之前就分流，这是两讲最根本的分工：

  • 第10 讲裁剪本讲溢出存储

纯文本这条边界划好了：超了阈值就外置，模型需要时按指引取回。

判据说完了，真要存的时候调的是服务，它只暴露一个动作 saveText，存进去，换回三样

东西：

javascript

  • 是什么要点

  • 消费方不解析它、只当黑盒。本地后端把它渲染成文件路径，换后端可能是 URI 或键；路径形如 <…

  • 后端给出的不透明定位符>/<​sha256(会话 id) 前 12 位 >/< 随机前缀 >-<​suggestedName>

  • 用来对账。示例里落盘 60016 字节，跟工具原本吐

  • 的一个字节都不差；saveText 自己不判阈值（判阈值存了多少字节的是上面那个策略插件），多大的文本都存得进去

retrievalHint

  • 告诉它"用 read 分段读，或用 grep 在这个路径里搜给模型看的检索指引

三样东西都在手上了，那是存的一方拿到的。存到外面之后，模型怎么看见它？文本这条路是“告诉模型自己去拿”。

那条结果被换成头尾各一小段预览，外加一句通知，就是前面说的那句“去哪儿读全文”，由

locator（全文在哪）和 retrievalHint（怎么读）两样拼成；剩下那一样 bytes 只用
来对账，不进上下文。都是纯文本，模型后面还想看，用 grep 就能翻。中间那部分一直在文

件里、随时能取回，外置不是丢弃，是把它换成“需要时取得到”。

图片的外部持久化：存成附件 ​

第二个问题：用户拖进来的一张截图，也该整份进上下文吗？

不该。图片的字节不落进日志，上下文里也只留一个引用，而且不论大小，一律外置。官方点名四种东西绝不允许进这本只追加的日志：

三种引用：blob: URL、宿主临时路径、提供方 URL，指向的东西易失效或不可控；
  • base64 数据：它则相反，不是引用，是数据本身，塞进日志会膨胀、还删不掉。

上面四类都被禁了，图片走的是另一条通道，dsh 给出的答案是附件（attachment）：先把字节存成不可变对象，日志里只留一个引用。这个引用和前面那三种不一样：它指向的是 dsh 自己先落盘的字节，对象就在 dsh 的盘上、随时能读回；那三种指向的是 dsh 掌控之外的东西，说没就没。

外置这一步没有阈值，不像文本那样超了才外置，图片不分大小、一律外置。而图片能不能真的存进去，是另一道关卡——准入，管的是类型、大小、像素、张数这些限制，不支持或超

了，直接报错（类型由后端按字节识别出的实际格式说了算，不采信声明的 mediaType）。

存进去有条硬规矩——先落盘，后追加事件：宿主必须先让图片真的落到磁盘上，才能把

user/message 写进日志（模型输出图片时同理），否则日志里就会留下一条指向不存在的对

象的引用。

javascript

// 存一张

// 存一批

准入线看完了。存到外面之后，模型怎么看见它？图片这条路是“发请求时才解析”，它在日志

里的形态是一个内容块（ImageBlock）：
interface ImageBlock {
 type: 'image';
 attachment: ImageAttachmentRef;  *// 只有引用和元数据，不含 base64*
}

真正把图片的字节读回来，发生在发请求给模型的时候：提供方的适配器会拿着引用去

readImage()，把字节转成 base64 放进请求。

所以它和文本那条路正好相反：文本是模型自己再发一次工具调用去取，图片则是 dsh 在发请求时自动解析、模型不用动手。根源就在“能不能被模型自己检索”：文本是纯文本，给它一条

路径，模型用 grep 就能自己翻；图片是字节，模型没法 grep 一张图。

本讲小结 ​

这一讲划下最后一条边界：工具的大段输出、用户拖进来的图片，都不该整份进上下文，dsh给它们各开了一条外置通道。

溢出存储（工具输出）只管纯文本：超阈值就整份存走，上下文里只留头尾预览和一句"去哪儿读全文"。

附件只管图片：先落盘、后追加事件，日志里只留一个 ImageBlock 引用，发请求时 dsh 才

解析回字节。

这，就是上下文边界的核心：入口处，大块内容（工具大段输出、图片）只进线索、不进全文，需要时再取回；进去之后，一旦逼近或越过窗口边界，就靠第 10 讲的压缩和裁剪腾地方。

到这里，核心篇：能力、工具与会话就收口了。下一讲进入编排篇：从 Agent 循环到多 Agent协作。
