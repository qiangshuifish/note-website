思考题答案合集 | 对答案的过程，比答案本身重要 ​

你好，我是 Tyler。

到今天，课程的正文内容已经接近尾声。为了方便大家查漏补缺，这次加餐我决定集中发布部分课后题的参考答案。

10 一次纠正，该放在哪一层？

Q：你在自己的业务里用 Hermes。有一次它查一个支付状态查错了，你当场纠正了一句。现在要判断这句纠正该沉淀到哪一层。

如果它只是记错了一个事实（这个渠道早就停了），该写进哪一层？如果它这次是步骤走错了，以后碰到同类问题按这个新步骤来就行，又该写进哪一层？还是说，你觉得这次纠正应该去训练模型？分别说说你的理由。

A：先看你纠正的是事实，还是做事方法。“这个支付渠道已经停用”是一条事实。核实后，如果后续任务还会用到，就更新 Memory 里的旧记录，注明适用环境和依据。如果团队有统一维护的渠道目录，就更新目录中的停用状态，让 Agent 查询时以目录为准。

“以后遇到同类问题，先查订单流水，再核对渠道回执”是一套可复用的方法，适合写进 Skill。除了执行步骤，还要写清适用条件，以及拿到不同结果以后怎么走。

更新 Memory 和 Skill 都属于本讲说的第一层。一次业务纠正通常用不到训练模型。如果同类错误在多种任务里反复出现，再用独立样本评估是否值得通过训练来解决。

11 复盘已启动，记忆文件为什么没有变化？

Q：会话包含已核实、后续仍有价值的新事实，后台复盘已启动，但记忆文件没有变化。怎样区分已有等价记忆、模型漏记和执行失败？

A：先检查后台实际收到的会话和复盘提示，确认新事实没有因快照时点或输入整理而缺失。再核对线程是否仍在运行，不能把等待超时当成已经结束。若线程已经结束，比较已有记忆是否包含同样意思；有等价记忆时，不重复写入可能是合理结果。没有等价记忆时，检查模型是否发起写入、请求参数是什么、工具回执是否成功，以及是否记录了异常。未调用写入且没有执行故障，才进一步排查模型漏记；已调用但返回失败，应处理执行问题。

成功回执与文件变化也要对应核对。仅凭文件没变化，不能直接判定是哪一种原因。

12 环境变了，Agent 怎样可靠地更新旧记忆？

Q：假设你负责一个 7×24 小时在线的巡检 Agent，平时自动巡检，告警来了负责排查和恢复。它已经在线上跑了一段时间，会把排查中沉淀的经验存下来，下次遇到同类问题直接复用。最近底层平台做了一次迁移，日志查询从原来的统一入口改成按区域、环境拆分，可Agent 排查时还是习惯性走旧入口；有时候同事临时给了一个能用的地址，它也会当成长期规则记住。

请你设计这套记忆维护的能力。希望达到的效果是，环境变了，经验能及时更新，不会拿着旧记忆误导排查；但也不能因为一次偶然成功就乱改，改了什么、为什么改，事后要查得清楚。

你可以谈谈整体思路、关键环节和容易踩的坑。

追问，如果让你基于现成的 Agent 框架来做，你会看重它提供哪些能力？

A： 这套机制需要解决两个问题：环境变化后及时修订旧记忆，避免继续使用失效规则；新经验写入前必须核实依据，避免把一次偶然成功固化为长期规则。

整体链路分为三个环节。

第一是在线执行。Agent 处理告警时，保留迁移说明、日志查询结果和工具回执，为后续修订提供原始证据。

第二是后台修订。任务结束后，通过 Background Review 对照新旧信息，确认环境变化是否影响已有记忆。发现失效规则后，定位具体条目进行修订，同时保留修改前的内容、证据来源和适用范围。对于尚未核实的临时地址，只保留为本次任务的上下文，不直接写成长期规则。

第三是修订生效。后台修改记忆文件，并不意味着正在运行的会话立即使用新内容。已经加载旧记忆的会话可能仍然沿用原有快照，后续会话才能读取更新结果。如果当前告警就需要使用新规则，应直接向当前会话提供经过确认的迁移说明。

记忆内容也需要控制粒度。对于日志入口迁移，应该优先记录“根据区域和环境查询服务目录”的稳定规则，具体地址由服务目录维护。这样后续再次迁移时，Agent 仍然能够找到正确入口。

框架选型上，我会优先考虑 Hermes 这类具有原生记忆机制的 Harness。它提供后台复盘、记忆编辑和会话加载能力，也支持对已有内容进行定位修改和容量检查。工程重点是建立修订依据、适用范围和验证规则，再通过典型任务确认旧规则已经失效、新规则能够正确生效。

13 故障处理有疑点，Agent 怎样查证并纠正？

Q：你们团队在 prod 环境运行着一个 7×24 小时在线的巡检 Agent，平时自动巡检，告警来了负责排查和恢复。它会在故障处理后写总结，最近却发现有些总结把“准备回滚”写成了“已经回滚”，同事据此复盘时，连服务到底怎样恢复的都说不清了。请你设计一套能力，让 Agent 在有人追问、或者发现总结有疑点时，能自己找回当时的记录，核实做过什么、结果怎样，再纠正总结。希望它不用每次都让人翻记录，也不用把所有历史重新读一遍；查不到的部分要如实说明，不能编出一个完整故事。

A： 先做需求分析。这个 prod 巡检 Agent 的核心诉求是让总结内容站得住：故障后写下的结论要能经得起追问，复盘时不能靠另一份总结自证。它需要一条按需、低成本回到原始会话核对的通道，避免事后总结偏离实际执行过程。

再做架构设计。先用事故号、服务名或时间窗口找到原会话，再从命中位置展开相关记录，按工具调用 ID 把请求和回执配对。看到“已受理”，就继续查异步任务的最终状态。看到“执行完成”，可以确认该动作已完成。服务是否恢复，还要看后续监控或探测。

查证以后，回到原事故总结补一条修订记录，写清原判断、修正后的结论，以及对应的会话和工具回执。比如，现有证据只能确认回滚请求已受理，是否执行完成、服务如何恢复，都暂时无法确认。以后还能复用的事实和方法，再分别沉淀到 Memory 和 Skill。

最后看 Hermes 怎样支持这套能力。Hermes 使用 state.db 持久化会话消息，借助 FTS5

进行关键词检索，并支持按需展开历史记录。结合工具调用 ID，可以将请求与回执对应起来，还原实际执行过程。后台复盘和 Memory 工具则支持后续经验沉淀。

在此基础上，业务系统需要补充事故记录关联、工具结果核验和总结修订流程，确保每一项结论都有原始证据支持。配套练习覆盖从会话定位、记录展开到工具回执配对和结果核对的完整过程，你可以动手试试看。

14 多个巡检 Agent 怎样可靠地共享记忆？

Q：你的团队准备为多个在线巡检 Agent 建立共享记忆系统。不同实例需要积累和复用执行经验，同时能够检索企业已有的手册、规范和技术文档。

请设计这套系统，重点说明三个方面：如何通过统一接口连接 Agent 与外部记忆后端；如何将不同实例的执行经历汇聚、提炼并共享；如何接入企业知识，并支持 Agent 在任务中自动召回和按需检索。

同时，进一步考虑系统的运行保障：如果一个实例已经完成任务，另一个实例却无法召回它的记录，应该怎样排查？如果外部记忆服务出现故障，又该怎样避免影响当前任务，并确保执行经历不会在后台悄然丢失？

A：先做需求分析。多实例共享记忆需要解决两个问题：一是让不同 Agent 积累和复用执行经验，避免重复排查；二是让 Agent 能够检索企业已有的手册、规范和技术文档。前者来自不断产生的执行经历，后者来自企业已有的知识资产，两类信息都需要能够被后续任务使用。

再做架构设计。系统通过统一的 Memory Provider 接口连接外部记忆后端。不同实例保留独立会话，将执行经历同步到共享后端，经过提炼和索引后形成可复用的案例与经验。企业知识则通过资料接入、解析和分层组织，支持自动召回与按需检索。共享范围由实例身份、用户权限和记忆命名空间共同控制。

接下来设计故障处理机制。读取和写入分别处理。外部记忆读取失败时，跳过本轮外部召回，使用当前上下文继续执行，避免影响在线任务。写入则需要可靠性保障：先将待同步的执行经历写入本地持久队列，再由后台向共享后端提交。每条记录使用实例、会话和轮次组成的稳定ID，支持幂等重试；只有收到成功回执后，才标记为已同步。持续失败的记录保留在队列中，并对同步积压和失败情况发出告警。

如果实例 A 已经完成任务，实例 B 却召回不到对应经历，就按数据链路逐步排查。先检查 A是否完成本地入队和远端写入，再确认后端是否完成提炼与索引，最后检查 B 的检索范围、权限和查询条件。这样可以区分记录未同步、已同步但尚未建立索引，以及记录可检索但 B无权访问等情况。

最后看 Hermes 怎样实现。Hermes 将外部记忆抽象为 Memory Provider，在会话启动时初始

化，每轮开始前通过 prefetch 召回相关记忆，轮次结束后通过 sync_turn 同步执行经

历。同一时刻只允许注册一个外部 Provider，具体存储、提炼和检索由外部后端完成。本地持久队列、幂等重试与失败恢复则需要在适配层或外部系统中实现。

在 OpenViking 适配器中，执行经历可以进一步提炼为长期记忆、案例和经验，企业知识则通过 L0 摘要、L1 概览和 L2 正文详情进行分层组织。配套练习先用文件后端验证 Provider 的读写流程和故障处理，再通过 SQLite 验证不同实例之间的双向共享，最后可以进一步接入OpenViking，验证自动提炼与分层检索能力。

15 Agent 怎样从故障排查中提炼技能？

Q：你的团队部署了一套 On-call Agent 系统。Agent 能够独立使用监控、日志、代码检索和测试工具排查故障，但经常需要几个小时、经过大量探索才能找到根因。

团队希望 Agent 在任务结束后，能够自主复盘完整的 Rollout，从中提炼新的诊断技能，供后续任务使用。

请设计这套自主技能学习机制：复盘 Prompt 应该寻找哪些学习信号，怎样把执行经历组织成包含步骤、工具调用和判断条件的 Skill，如何排除不可靠的经验，以及怎样确定新技能的适用范围。

进一步考虑，如果调查没有产生可靠的诊断流程，是否还应该创建 Skill？怎样避免将一项技能拆成多个只适用于单次故障的文件？

A：先做需求分析。自主技能学习要解决的是怎样从长程 Rollout 中提炼新的可复用能力。新Skill 应面向一类任务，保存操作步骤、工具使用方式和关键判断条件，而不是直接记录某次事故的调查过程。

再设计复盘 Prompt。引导模型寻找新的有效技术、调试路径、工具使用经验和用户纠正；随后按照 Procedure first 原则组织执行流程，将经验教训放在相关步骤中。同时，要求新 Skill去除一次性任务信息，并排除临时环境错误和未经验证的失败操作。

最后完成技能创建。后台先检查是否已有覆盖同类任务的 Skill，避免重复创建。确认需要新建

后，通过技能管理工具生成 SKILL.md，写明适用场景、操作步骤和判断条件。具体查询方

法和工具说明放进参考文件，支持按需读取。如果没有产生可靠的新技能，就不必创建文件。

这套机制沿用前面介绍的 Background Review，由复盘 Prompt 指导模型从执行经历中提炼技能，再通过工具将结果持久化。至于已有 Skill 怎样吸收新经验、修订判断规则并持续演进，则留到下一讲。

16 告警变复杂，Agent 怎样更新技能并保留原有能力？

Q：你已经有一套由 Harness 和 Skill 组成的 On-call Agent 服务。系统持续接收监控告警，由Agent 自主查询指标、日志和调用链，完成故障诊断。

最初，Agent 主要处理单条告警。随着业务系统规模扩大，一次故障开始触发多个服务的关联告警。原有 Skill 仍然逐条分析，重复进行大量查询，也无法有效识别故障传播路径。

团队希望系统能够从新的 Rollout 中发现这类任务变化，增量修订已有 Skill，让 Agent 掌握多告警关联研判能力，同时保留原有的单告警诊断能力。

请设计这套增量 Skill 演化机制：怎样从持续产生的执行记录中发现技能缺口，如何将新的判断条件和执行步骤融入已有 Skill，以及怎样验证修订后的技能仍然适用于原有任务。

进一步考虑，多个 Agent 实例同时发现类似缺口时，怎样组织修订，避免产生冲突？如果新增的关联研判流程改善了复杂故障处理，却影响了原来的单告警诊断，又应该怎样处理？

A：先做需求分析。增量 Skill 演化要解决的是实际任务分布变化与已有技能能力范围之间的偏差。系统需要从持续产生的执行经历中发现新的任务条件，识别原有 Skill 的缺口，再将有效经验转化为程序记忆的修订内容。

再设计反馈分析机制。Harness 汇总 Rollout，关联告警类型、Skill 使用记录、工具调用和诊断结果，识别反复出现的新任务模式。对于多告警事件，Agent 反复进行额外的服务拓扑和调用链查询，就表明原有诊断流程需要增加关联分析步骤。

接下来设计技能修订流程。后台通过 Background Review 提炼新的判断条件和执行步骤，找到需要修改的已有 Skill。修改前读取当前文件，再通过局部补丁将新流程融入原有步骤，让单告警和多告警任务能够根据事件范围进入不同的诊断路径。相关参考文件也需要同步更新。

最后建立验证机制。使用历史单告警任务和新增多告警任务进行回放，检查诊断路径、工具调用和根因判断结果。对于多个实例提出的修改，先汇总形成候选版本，统一验证后再应用到服务；如果新版本影响原有任务，则恢复原有版本并重新调整。

通过这套机制，Harness 将持续产生的执行反馈转化为技能修订的依据，Skill 则不断完善诊断策略，让 Agent 服务适应越来越复杂的故障场景。

17 技能越积越多，Agent 怎样持续优化技能库？

Q：你已经有一套由 Harness 和 Skill 组成的 On-call Agent 服务。随着自主学习持续运行，技能库积累了大量诊断 Skill，其中部分能力高度重叠，还有一些长期没有活动。

系统已经启用了 Curator 的自动状态管理、语义整合和内置技能清理，希望在不依赖人工逐项整理的情况下，持续优化技能库结构。

请设计这套自动整理机制：怎样根据活动记录管理技能生命周期，怎样利用模型判断哪些 Skill应该整合，如何建立共同入口并保留专用能力，以及怎样确认整理没有破坏原有任务的执行。

进一步考虑，长期不用的应急技能应该怎样保护？如果两项 Skill 合并后，原有参考文件或脚本无法访问，怎样发现问题并恢复？

A：先做需求分析。Skill Curation 要解决的是技能库持续增长带来的重复内容、选择困难和无效技能积累。整理后的技能库应当让 Agent 更容易找到正确的 Skill，同时保留完成任务所需的关键规则和支持文件。

再设计生命周期管理。系统持续记录 Skill 的使用、查看和修改情况，根据活动时间自动标记

和归档长期未活动的技能。重要的应急 Skill 通过 pin 保护，避免因使用频率低而被归档。内

置技能的自动清理采用同样的活动管理思路，但不参与模型的语义整合。

接下来设计模型整合。Curator 通过后台 Agent 阅读候选 Skill，按照任务类别寻找共同入口。对于能够整合的技能，合并重复流程，将独有经验融入对应步骤，并把专用的参考资料和脚本迁移到共同 Skill 中。不同职责和权限范围的技能仍然保留独立入口。

最后检查整理结果。完成内容迁移与引用更新后，再归档旧 Skill。通过典型任务验证 Agent能否找到新的入口，并正确读取所需的专用内容。系统同时保留归档文件、运行记录与整合前快照，支持后续恢复和回退。

通过这套机制，Hermes 能够在自主创建、修订 Skill 的基础上，进一步自动维护整个技能库，让持续积累的能力保持清晰和可用。

18 Skill 升级后，怎样确认新能力有效、旧能力没退步？

Q：你已经有一套由 Harness 和 Skill 组成的 On-call Agent 服务。Agent 能够自主分析监控告警、查询日志和调用链，并定位故障根因。

最近，系统为原有 Skill 增加了多告警关联研判能力。新版能够更好地分析多服务故障，却在部分原有单告警任务中出现了跨集群告警关联错误。

团队希望在采用新的 Skill 版本前，通过业务 Eval 判断这次修改是否真正改善了服务能力。

请设计一套 A/B 对照评测机制：怎样准备同时覆盖新旧任务的测试集，如何控制不同 Skill 版本的执行条件，以及怎样从结果、工具轨迹和业务证据中判断任务是否正确完成。

进一步考虑，如果新版在新增任务中明显改善，却在个别关键旧任务上退步，应该怎样决定是否采用？如果评分器本身出现误判，又该如何发现并修正？

A：先做需求分析。业务 Eval 要回答的是 Skill 修改对任务执行产生了什么影响。评测需要同时覆盖新增能力和原有任务，通过实际结果判断新版是否改善了目标场景，以及有没有引入回归错误。

再设计 A/B 对照。保存旧版和新版 Skill，让两个版本分别在独立的执行环境中处理同一组任务。固定模型配置、任务输入、预置记忆和工具数据快照，评测期间关闭后台学习。对于存在随机性的执行过程，重复运行并保留逐次结果，避免依赖单次表现。

接下来设计业务评分。将根因服务、环境、集群、告警归属和证据编号等客观字段交给规则或脚本核对；对于解释质量和证据充分性，采用模型或人工评分。同时使用已知正确和错误的结果校准评分器，确保它能够识别跨集群关联、根因颠倒和证据不一致等错误。

如果评分器出现误判，先拿原始回执和人工标注复核，修正并记录评分器版本。然后用同一版本的评分器、同一组任务重新评估新旧 Skill，再做采用决定。

最后建立采用决策。用开发用例检查已知问题是否解决，再通过留出用例检查泛化和回归。综合任务正确率、执行耗时和工具调用成本判断新版是否满足要求。

候选 Skill 要在新增任务上达到预期，并且在原有关键任务上通过回归检查。任一关键任务出现退步，就保留旧版，继续修订和评测。

通过这套机制，Agent 每次自主创建、修订或整理 Skill，都能够通过可重复的业务任务检验结果，为持续自进化建立可靠的评测依据。

19 真实告警怎样变成可靠、可复现的评测集？

Q：你的团队已经部署了一套持续运行的 On-call Agent 服务。系统每天处理大量真实告警，并留下执行记录。其中一部分任务出现了根因误判、跨集群告警关联或证据不足等问题。

团队希望把这些真实经历整理成企业评测数据集，让以后每次修改 Skill，都能重新执行同一批任务，检查已知问题是否修复，以及有没有引入新的错误。

请设计这套数据集建设机制：怎样从生产 Rollout 中筛选代表性任务，如何固定当时的监控、日志和调用链数据，怎样建立独立的正确答案，并将这些任务接入可重复运行的业务 Eval。

进一步考虑，如果一条历史记录只有最终结论，没有完整故障快照，能不能直接加入评测？如果 Agent 当时给出了错误诊断，却没有被值班人员纠正，能不能把它作为标准答案？随着数据集不断更新，又怎样保证新旧 Skill 使用相同的测试条件？

A：先做需求分析。企业评测数据集要解决的是怎样将真实执行经历转化为可重复运行、具有明确评分标准的任务。Rollout 虽然包含 Agent 的执行过程，但只有任务输入、故障快照和独立标准答案都具备，才能形成正式评测用例。

再设计数据回收流程。通过 Langfuse 收集执行记录，由企业程序按故障事件归组、筛选和去重。数据集既要覆盖常见故障，也要保留跨集群、多告警和证据不足等关键场景。无法还原现场或缺少可靠答案的记录，先保留为待处理任务。

接下来构建可重放用例。保存完整的任务输入，将监控、日志、调用链和服务依赖关系固定为可查询的故障快照，使不同 Skill 版本能够从同一现场自主调查。标准答案根据独立故障证据确认，并与 Agent 输入隔离；原报告和历史反馈可以用于复盘，但不直接充当正确答案。

最后管理数据集版本和评测执行。通过 Skill Up 加载固定故障快照，使用统一评分器运行新旧Skill。每次比较都固定任务、快照和评分规则的版本；用例新增、修订或停用时保留来源及变更记录。开发用例与留出用例分别管理，保证后续仍能检验 Skill 对其他同类故障的处理能力。

这样，真实 Rollout 就能够持续转化为可重复执行的评测任务，让 Agent 的后续自进化建立在可靠的业务数据基础上。

20 怎样用 GEPA 自动优化 Skill，并选出可靠版本？

Q：你的团队有一个长期运行的 On-call Agent，它通过一份 SKILL.md 执行告警诊断。现

在，你已经积累了一批测试任务，包括普通告警、多告警关联和跨集群故障，每条任务都可以运行并评分。

团队希望利用 GEPA 自动优化这份 Skill，而不是继续依靠人工反复修改。

请设计这套离线优化流程：怎样让 GEPA 根据执行反馈提出 Skill 修改，怎样通过候选接受与帕累托选择探索不同版本，以及怎样将 GEPA 与现有 Agent 的执行过程连接起来。

追问：如果优化结束后任务得分提高，但导出的 SKILL.md 没有变化，可能是什么原因？如

果两个候选分别擅长不同任务，为什么不应该立即只保留平均分最高的一个？

A：首先，将 Skill 正文作为可优化的文本参数，并准备能够运行和评分的测试任务。GEPA从当前候选出发，执行训练任务，读取轨迹与反馈，再由反思模型提出修改。候选通过小批次接受检查后，进入验证评测。

搜索过程中，GEPA 根据不同候选在各道验证题上的表现进行帕累托选择，让多个具有不同优势的版本保留继续探索的机会，而不必始终只沿着当前平均分最高的版本修改。

工程接入通过 GEPAAdapter 完成。evaluate 负责让 Agent 使用候选 Skill 执行任务并返回
评分与轨迹，make_reflective_dataset 则将这些执行结果转化为反思材料。
如果分数涨了，但导出的 SKILL.md 没变，先确认涨的是哪一阶段的分。某个候选可能只在

小批次或个别题上更好。本讲的配套练习要求最终候选的验证分严格超过基线，且 Skill 正文有变化，才导出新正文。还要检查 GEPA 实际优化的字段。如果优化的是外层提示，Skill 文件也可能保持原样。

最后核对最终选中的 skill_body、评测时 Hermes 实际读取的 Skill 正文和导出的文件正

文。通过内容哈希确认三者一致，再使用独立任务检验优化效果。这样，系统能够根据批量任务反馈自动改进 Skill，并在保持底层模型参数不变的情况下，选出经过验证的版本。

21 SkillClaw 怎样把多个 Agent 经历提炼为可靠技能？

Q：你的团队在两个机房部署了 Hermes On-call Agent，两个实例使用相同的超时诊断 Skill，却分别处理不同的故障。

实例 A 在完成健康检查和上游延迟查询后，没有定位原因，只建议继续检查连接池；实例 B在相似条件下实际查询了连接池，发现资源等待，并进一步检查连接的占用与释放情况。

团队希望使用 SkillClaw，将这两段执行经历汇入共享后端，自动提炼成一份更完整的超时诊断方法。

请设计这套机制：Client Proxy 怎样记录多个 Hermes 实例的在线会话，Evolve Server 的Summarize、Aggregate、Execute 分别处理什么内容，以及怎样确认最终产生了哪些 Skill 修改。

进一步考虑，为什么不能把实例 A 的连接池检查建议直接当作已验证方法？实例 B 的实际执行记录又能够补充哪些信息？

A：首先，分别为两个 Hermes 实例接入 Client Proxy，让模型请求经过代理，并将完成的会话归档到同一共享组。代理通过连续的模型交互记录工具调用与回执，不需要接管 Hermes 的工具执行过程。

接下来，由 Evolve Server 运行 workflow 引擎。Summarize 分别提炼两段经历，明确实例

A 只提出检查建议、实例 B 实际执行了连接池查询；Aggregate 对齐两段经历的共同条件，归纳出在初始检查无法解释超时时补充连接池查询的改进方向；Execute 将新的诊断步骤写入已

有 timeout-triage，或根据需要创建新 Skill。

实例 A 的经历支持判断现有方法存在流程缺口，但不能证明连接池异常构成故障根因。实例 B的工具调用和回执则提供了可执行的后续检查路径。结合两段经历，能够形成包含触发条件、查询步骤和结果解释的方法，而不是将一次任务的结论直接写成通用规则。

最后，通过共享存储中的会话材料、Evolve Server 的处理历史和实际 SKILL.md 内容，检查

是否完成了预期的技能修订。会话上传与 Skill 演化是不同的阶段，是否产生修改应以实际处理结果为准。

22 共享 Skill 发布后，怎样验证新方法真正生效？

Q：你的团队部署了多个 Hermes On-call Agent，它们通过 SkillClaw 共享一套超时诊断Skill。

最近，Evolve Server 根据某些实例的真实经历，为 timeout-triage 增加了连接池检查。

现在，希望让其他实例在不重新经历原始故障的情况下，直接获得并使用这项改进。

请设计从 Skill 发布到实际生效的流程：怎样选择 Direct 或 Validated 模式，如何让接收实例自动获取新版本，以及怎样通过相同故障任务的对照实验，确认新增方法真正进入了工具执行过程。

进一步考虑，如果接收实例已经下载了新版文件，却没有执行连接池查询，你会怎样区分 Skill未加载、任务不满足触发条件，以及 Agent 没有正确执行方法这几种情况？

A：先确定发布模式。Direct 将接受的演化结果直接写入正式共享技能库；Validated 则先创建候选验证任务，由启用验证功能的客户端在后台评估，满足发布条件后再进入正式技能库。

在隔离的教学或实验组里，如果想先观察演化结果怎样同步，可以用 Direct。对于多个在线实例共用的关键诊断 Skill，我会选择 Validated，并增加独立的业务回放作为正式采用的门槛。

接下来，在接收实例上配置正确的共享组和存储后端，先通过 list-remote 和 pull 确认

手动同步正常，再开启启动时自动拉取与周期性轮询。不同实例仍保留自己的本地 Skill 目录，由 Client Proxy 负责同步正式共享版本。

然后进行业务对照。使用相同故障输入和工具数据，分别运行旧版与新版 Skill，检查任务是否满足连接池检查的触发条件，以及新版是否实际发起连接池查询。比较的重点是工具调用、原始回执和最终判断，不能只看 Agent 是否在回答中提到了连接池。

接收实例已经下载新版，却没有执行连接池查询时，依次检查三个环节。

首先检查 Skill 加载。启动新会话，通过 skill_view 读取实际可访问的 Skill 正文，与已发

布版本比对，必要时计算内容哈希。如果仍然读取旧版，就继续排查文件同步、加载路径和会话缓存。

其次检查触发条件。核对健康检查和上游延迟查询的真实回执。如果上游异常已经解释超时，跳过连接池查询符合 Skill 的执行规则。

最后检查实际执行。如果前置检查都无法解释超时，并且满足新版 Skill 的其他触发条件，Agent 仍然没有发起连接池查询，就记录为方法执行失败。如果已经发起查询，却没有取得有效回执，则继续排查工具执行问题。

如果新版出现回归问题，就从历史记录或备份中恢复已知可用的 Skill，重新发布并同步到客户端，再通过新会话确认恢复效果。

通过这套机制，一个 Agent 的执行经历就能够经过离线演化，形成可共享的 Skill，并让其他Agent 在后续任务中真正复用这项改进。

23 多个 Agent 怎样持续学习、验证并安全发布新技能？

Q：你的团队部署了多个 Hermes On-call Agent，希望将长期记忆、Skill 自进化、GEPA 离线优化和 SkillClaw 跨实例共享整合为一套持续演化系统。

请设计从任务执行、经历回收、Skill 候选生成、版本评测到正式发布的完整流程，并说明怎样让新版本的执行结果继续进入下一轮演化。

进一步考虑，如果候选评测失败，或者已发布版本出现退步，系统应该怎样保证在线任务不受影响？

A：整体系统分为在线执行、经历积累、技能演化、业务验证和版本发布五个环节，让 Agent的日常执行不断产生新经验，再将经过验证的经验转化为可共享的工作方法。

首先是在线执行。多个 Hermes 实例使用正式版 Skill 处理告警，通过 Memory Provider 召回相关历史经验，并保留工具调用、原始回执和实际使用的 Skill 版本。各实例独立执行任务，共享经过授权的长期记忆和正式技能。

其次是经历积累。任务结束后，执行记录同步到外部记忆后端。经过核验的事实和任务经验沉淀为长期记忆，供后续任务召回；完整 Rollout 同时作为技能演化的输入。长期记忆负责提供事实和历史经验，Skill 则保存可重复执行的诊断流程和判断条件。

接下来是技能演化。SkillClaw 汇聚多个 Hermes 实例的执行经历，通过 Summarize、Aggregate 和 Execute 提炼改进方向，生成新 Skill 或修订已有 Skill。GEPA 则利用历史评测任务执行离线优化，根据任务反馈和执行轨迹搜索更好的 Skill 正文。两种机制可以分别产生候选，统一进入后续验证流程。

然后是业务验证。不同来源的候选统一记录版本、修改内容和来源，通过 Eval 与当前正式版进行对照。测试集同时覆盖新增任务和原有关键任务，固定模型配置、工具数据和评分规则，检查诊断正确率、执行成本以及关键任务的回归情况。候选只有通过验证，才能进入正式发布流程；未通过的版本继续留在候选区，不影响在线服务。

最后是版本发布。经过批准的 Skill 写入正式共享技能库，通过 SkillClaw 同步到其他实例。系统在任务启动时固定本次执行使用的 Skill 版本，新版本由后续任务加载，避免同一个任务执行过程中混用不同版本。每次执行都记录实际加载的版本、工具回执和任务结果，再送回记忆后端和技能演化流程，形成下一轮学习的输入。

运行保障的关键是将后台演化与在线执行隔离。候选生成、GEPA 搜索和业务评测都在独立环境中进行，评测失败不会改变在线版本。如果已发布版本出现回归，就重新发布上一个经过验证的版本，让接收实例同步，并通过新会话确认实际加载内容及关键工具行为。

这样，Memory 持续积累事实和执行经验，Skill 将可靠经验沉淀为可复用的方法，GEPA 与SkillClaw 负责优化和共享，Eval 控制版本质量，Harness 则将这些能力连接成持续运行的闭环。Agent 每完成一次任务，都有机会为下一次任务提供经过验证的改进。

综合实战 远程 Agent 怎样实现多端协同与故障恢复？

Q：某公司计划建设一个面向企业用户的 AI Agent 平台。用户可以通过 Web、Desktop 和CLI 等不同客户端访问 Agent，也可以在不同设备之间切换，继续查看和操作此前启动的任务。

Agent 运行在远程计算节点上，部分任务可能持续数小时，执行过程中会不断调用模型和外部工具。用户可以随时查看执行进度、补充指令、中断任务或重新连接。平台还需要支持多个Agent 在不同机器上独立运行，并在运行节点异常或重启时尽可能恢复尚未完成的任务。

请你作为系统设计负责人，设计这套平台。重点说明多客户端如何共享同一任务状态、多个用户操作如何协调、长时间运行的任务如何保证连续性，以及运行节点发生故障时如何恢复执行。同时考虑系统的扩展性、资源调度和数据安全。

A：参考答案（打出加粗采分点即可）

首先明确系统的核心对象，区分用户、客户端、Agent 运行实例、会话和具体任务。一个用户可以拥有多个 Agent 运行实例，一个运行实例可以管理多个会话，每个会话又可以包含多项任务。不同客户端访问同一个会话时，应当读取同一份权威状态，而不是各自维护独立的执行历史。

在此基础上设计控制平面与执行平面分离的架构。控制平面负责身份认证、运行实例注册、会话定位、资源调度和状态管理；执行平面负责模型推理、工具调用和任务执行。通过统一的接入接口连接 Web、Desktop 和 CLI 等客户端，并通过服务发现和调度机制将请求路由到对应的运行节点。

对于多客户端状态一致性，需要为每个会话建立唯一标识，并指定唯一的执行所有者。多个客户端可以同时订阅任务进度，但对同一会话的写操作需要经过统一协调。可以采用单写者机制和命令队列，对用户指令进行排序，避免多个客户端同时修改任务状态造成冲突。对于需要立即生效的中断指令，应提供独立的控制通道，避免其被普通任务消息长期阻塞。

对于长时间任务的状态管理，不能只依赖运行进程的内存。需要将任务状态、事件记录和执行结果持久化。可以采用事件日志记录任务创建、模型调用、工具请求、工具返回和状态变化，并定期生成检查点，减少故障恢复时需要重放的数据量。客户端重新连接时，根据最后接收的事件序号获取增量记录，必要时先获取状态快照，再继续接收实时事件。

对于节点故障与任务恢复，需要区分会话历史恢复和实际任务恢复。节点异常退出后，调度服务通过心跳和租约机制识别故障节点，将符合条件的任务重新分配给其他节点。新节点根据最近一次检查点和事件日志恢复任务状态，再判断下一步执行操作。对于已经完成的工具调用，不能仅凭模型上下文判断是否需要重试，而应检查实际执行记录和外部系统状态。

尤其需要解决重复执行与操作幂等性问题。分布式环境中，任务可能因为超时、消息重复投递或节点故障而被多次触发。平台应为具有副作用的工具调用生成唯一请求标识，通过幂等键、执行状态记录和结果核对避免重复产生业务影响。对于无法确认执行结果的操作，应进入待核实状态，而不是直接重新执行。

对于运行节点调度与扩展，需要根据节点负载、可用资源、运行环境和任务类型进行调度。可以通过心跳维护节点健康状态，通过队列控制待执行任务数量，并根据并发量动态扩展执行节点。已经运行的会话应尽量保持节点亲和性；确实需要迁移时，先完成状态持久化，再通过租约和版本校验确保同一会话不会同时在两个节点上执行。

对于服务可靠性与资源隔离，需要为不同用户设置并发配额、计算资源限制和模型调用预算，防止个别用户占用过多资源。对模型服务和外部工具设置超时、重试及熔断机制，避免外部依赖故障影响整个执行平台。节点退出时采用优雅关闭，停止接收新任务，并等待当前任务完成或保存恢复所需的状态。

最后建立完整的可观测性体系。通过统一的任务 ID、会话 ID 和请求 ID 关联客户端请求、调度过程、模型调用和工具执行记录。重点监控任务排队时间、节点负载、会话恢复成功率、重复执行率、任务完成时间和资源消耗。当出现任务中断或状态不一致时，能够从完整事件记录中还原执行过程，定位问题。

通过上述设计，平台能够将多个客户端、远程运行节点和长时间任务组织成一个统一的执行体系，在支持跨设备访问和水平扩展的同时，保证任务状态的一致性、执行过程的可恢复性以及外部操作的可靠性。
