自我进化，Agent的下一道分水岭 ​

你好，我是 Tyler。

这两年 Agent 这个方向变化很快。比如 Harness、RSI、FDE 这几个词就引发了不少讨论，它们听上去新鲜，骨子里却和咱们专栏前面聊过的内容连在一起。

今天，我就顺着专栏从前到后的脉络，把这 3 个词分别讲清楚，它们各自是什么，彼此又是什么关系。

从企业里的上下文工程，到每个人手上的 Harness ​

先聊 Harness。回到专栏最开头，我们花了不少篇幅讲企业级大模型系统的架构，还画了一张工业级全景图。它要回答的核心问题是，怎么在企业内部用上下文工程，把大模型和真实的业务工作接起来。

这张图里有一块叫提示语引擎，我们在 2023 年更新的第 19 讲里，把它叫智能体本体。你给它一个指令，它先得弄明白你到底想干什么；再从知识、工具、示例和聊天记录里，挑出眼下用得上的那些，在提示词里布置好、放进不同的逻辑分区，这就组成了模型这一轮真正看到的输入。要是信息还不够呢，它就自己去调工具、查资料，把结果带回来进入下一轮。就这么一轮一轮往下转，直到把问题解决，把答案交到你手上。

今天大家熟悉的 Agent Harness，做的其实就是这件事，它并不是凭空冒出来的。当年那个提示语引擎（Prompt Engine）在云上，就已经能接工具、能一轮轮迭代，能把一件任务从头做到尾，跟今天的 Harness 本质上是一回事。

真要说区别，只是它那时候部署在企业的云端，离普通使用者还比较远。再往后，工具怎么接有了 MCP 这样的标准，怎么组织上下文也慢慢沉淀成上下文工程这套方法，东西一样样规范化了，大厂才把它从云端下放到每个人的设备上。

下放到端上之后，每个人在自己的设备上就有了一个 提示词引擎（Prompt Engine）。一件任务怎么开头、怎么往下走，新指令从哪一刻开始算数，工具怎么跑，状态怎么存，遇到危险动作怎么拦，最后拿到什么结果才算完，这些它都在本地替你安排妥当。你不用一步步盯着，一件件工作它自己就做下来了。这就是 Harness。

单看一件任务，你可以把 Agent 拆成两半，一半是模型，负责理解、判断和生成，另一半是Harness，负责安排每一轮输入、接上环境、动手干活、存好状态，把能做的事圈在范围里。

RSI，在线离线架构在 Harness 上的样子 ​

前面说的，是 Agent 怎么把一件任务做好。可一件任务做得好，不等于它会从经历里越变越好。你多半遇到过这种情况，同一个地方它犯了错，你当场纠正，它也改了，可这次纠正只留在原来那段对话里。等换一件新任务，它又会重蹈覆辙。

你可能会想：那干脆把旧对话都带给下一件任务行不行？

也不行。上一次的具体参数、临时判断、当时的结论一股脑进了新现场，它反而分不清哪些只属于上一次、哪些今天还管用，过时的信息一样会把它带偏。一次经历要真能影响以后，中间得经过整理、审阅和验证。

要让经历这样沉淀下来，靠的是专栏里另一套架构，在线系统和离线系统怎么配合。我把离线叫 AI 系统的弹药库，在线叫冲锋队。在线面对正在发生的请求，当场读状态、调模型、给结果；离线把日志、行为、反馈收拢起来，做数据、训模型、评效果，再把验证过的新版本交回在线。这套架构最值钱的地方，是它构成了一个能持续变好的闭环。

RSI 落到 Harness 上，就是前台和后台，Hermes 就是这么做的。前台不停产生对话、动作、工具结果、人的纠正和验收，后台从这些材料里捞出可能有用的经验，整理、评测、审核，再把靠谱的新版本交给以后的任务。

那 RSI 到底是什么？它是 Recursive Self-Improvement，递归自我改进，说的是一个系统能改进自己，改进后的新版本再去做下一轮改进，能力一圈圈往上叠。这很像编译器自举，一个编译器能编译出自己的新版本，新版本再编译更强的版本。

很多人第一反应，是回去重训模型，拿 Agent 跑出来的数据训练下一代，下一代再回到系统里产生新数据。这条路不是走不通，只是又远又间接，中间隔着数据采集、训练、算力一大堆环节，一轮反馈走下来，信号传递的效率很低。

更直接的位置，其实就在 Harness 这一层。一个写代码的 Agent 本来就会写程序，它可以直接去开发下一代写代码的 Agent，递归关系是现成的。再往细里看，技能就是这个 Agent 的程序记忆，技能更好，任务就完成得更好，也就能产生更高质量的轨迹，这些轨迹回过头又沉淀成更好的技能，去服务下一批任务。你看，这一圈是能自己转起来的递归结构，Hermes 已经把它做出来了。

顺着这个递归结构看，自我改进可以分成 3 层。

  1. 记住一个新地址、一条新事实，改的是 Agent 掌握的信息；

  2. 把一条检查沉淀成技能，改的是处理问题的方法，技能飞轮就在这一层；

  3. 再往外，连怎么从经历里提炼技能这套方法本身都改变了，改的就是产生方法的方法。

所以我建议大家，从现在开始就用 Hermes 这类以 RSI 为目标的 Harness 框架。挑一件手头真实的工作交给它，让它在前台干、在后台复盘，看着经验一条条沉淀、下一次又怎么被用上，RSI 是什么感觉，你用着用着自然就有了。

FDE，PMF 中的自然产物 ​

讲完 Agent 自己怎么干活、怎么变聪明，还有一个问题，这套能力怎么真正进到一个个产业现场。这其实是专栏很早就碰到的问题。

在我们专栏的第 30 讲，我把 AI 进产业现场比成空军打巷战。好用的模型和平台攥在少数几家科技公司手里，真实需求却散落在一个个行业、一家家企业、一条条流程里，靠昂贵的专家蹲在现场一点点定制，这样的交付根本没法规模化。

那几年，各方其实选了不同的路。做模型的科技公司回去深耕模型能力，各个行业也回去忙自己的事。我当时的判断是，这道缝靠谁硬填都不划算，只有等科技公司真正做出让行业不得不用的能力，局面才会松动。

这个临界点，就是大家常说的 Product Market Fit，产品被验证真正满足了市场需求。科技公司真做出行业不得不用的能力，Harness 这类产品就算跨过了这道坎。今天企业开始允许员工用 Harness，还主动邀请科技公司一起做 AI 建设。正是这个契合已经发生的信号，能力端和需求端这两头，终于开始往一起走。

FDE 不是 PMF 之前就有的角色，它是产品跨过这道坎之后，才自然长出来的。方向还没验证的时候往现场派人，那是在帮着找产品；可方向一旦成立，要把一个通用平台规模化地落到一个个特殊现场，光靠标准产品就不够了，得有人在平台之上，把最后一公里的部署、集成和定制接住，这就是 FDE，Forward Deployed Engineer。

他们会直接扎进客户现场，陪着一起发现问题、设计系统、写代码、做评测、上线，最后再移交。现场干的活还得能沉淀回产品，规矩沉淀成技能，能力封装成工具，边界写进规则，验收固化成评测。

在自进化这套结构里，FDE 就像现实世界和演化系统之间的一个接口。他得判断清楚，哪些只是某次事故里的环境事实，哪些已经是能复用、还能跨环境传播的办法。现场那句“这样做就行”，需要变成系统能一遍遍执行的验收标准。现场经验经过这么一道把关，才能从某个人的手艺，变成可以反复复用的能力。

所以规模化交付的关键，也不再是往现场塞更多专家，而是让现场摸出来的办法进到后台，被整理、验证、发布、治理，再去服务下一批现场。

想真正体会这个角色的工作，最好的办法是把 Hermes 这类框架用好，在真实业务的落地过程里亲手走一遍集成。平台能接住什么，现场又要补什么，做过一遍，FDE 到底在干什么，你心里自然就清楚了。

当 Agent 渐渐无所不能，我们和它是什么关系 ​

聊到这儿，这 3 件事其实指向同一个画面。Agent 能靠 Harness 自动完成长程的工作，能靠RSI 从经历里越变越聪明，还能跟着 FDE 因地制宜，走进一个个具体的业务场景。

这时候一个问题会自然冒出来，原本在这个岗位上干活的人，和这个渐渐无所不能的 Agent，到底是什么关系。

我自己的答案，是把它当成你的数字分身。你自己坐在屏幕前的时候，其实默默扛着好多事。你记着任务最初要解决什么，知道哪些文件能改、哪些系统只能看，一个新要求来了，是立刻生效还是等这步走完，你心里也有数。工具返回了什么，你还会盯着，再根据测试、监控这些独立的结果，决定认不认它干的活。

可人一走开，这些责任不能跟着你一起走掉。目标得有人继续盯着，状态得能续上，动作要有边界，方向要可控制，最后结果还得有人验收。

理想的分身，像孙悟空拔根汗毛吹出来的小猴，把行动范围伸得更远，却从头到尾听他的、为他办事；另一种结果像六耳猕猴，长得一样、本事差不多，做的选择却已经代表不了孙悟空。Harness 要接住的，说到底是这份责任。

这些责任散落在模型调用、任务历史、工具执行、外部检查等不同位置，靠把提示词写长一点是接不住的。具体的产品会一茬一茬换，可这些职责一直都在。

小结 ​

最后，咱们做个小结。

这几个词听着新鲜，其实正好对应咱们专栏一步步走过来的 3 件事。最开始，我们讲在企业内部用上下文工程把大模型和业务接起来，这套能力今天下放到端上，就是 Harness；接着讲在线和离线怎么配合、让系统持续变好，落到 Harness 上就是 RSI；再后来讲能力怎么走进一个个产业现场，跨过 PMF 之后，最后一公里由 FDE 接住。路还是那条路，只是从企业云端走到了每个人手上。我们想要的，始终是一个可控、可验收的数字分身。

这门专栏我们前前后后打磨了很久，几年下来，一直有新同学加入，也有老朋友一直都在，把新老读者都服务好，是我们最上心的事。
