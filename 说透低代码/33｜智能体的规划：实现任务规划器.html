33 | 智能体的规划：实现任务规划器 ​

你好，我是陈旭。

上一讲，我们进行了一次非常特别的“纸上谈兵”。我们都化身为了“智能体设计师”，为我们即将构建的 AI Agent 的大脑——任务规划器（Planner），绘制了一份极其详尽的设计蓝图。从区分简单指令与复杂目标的“分流器”，到指导 LLM 思考的“终极元提示”五大要素，再到解决步

骤依赖的 $steps 引用语法，我们把理论武装到了牙齿。

那份蓝图，就是我们 Agent 智慧的源泉。它定义了我们的 Agent 应该如何思考，如何将一个宏大的目标，拆解成一步步具体、可执行的动作。

设计图纸已经完善，那么今天，我们的角色就要再次转换了。让我们一起从“设计师”变回“工程师”，将上一讲的每一个理论模块，每一个精巧构思，都逐一地、坚实地构建出来。

本讲的使命非常明确：将理论变为现实。当这一讲结束时，我们的 Awade 低代码平台将拥有一个真正意义上的“大脑”，它能够接收一个复杂的用户目标，然后自主地“思考”，并最终生成一份结构清晰、逻辑严密的 JSON 行动计划。

让我们开始吧！

第一个工具函数：编码实现“状态摘要”生成器 ​

还记得我们上一讲反复强调的吗？直接把又长又复杂的页面状态 JSON 丢给 LLM，就像是逼一位建筑师去读采购清单，效率低下且抓不住重点。所以，我们的第一项工程，就是实现那个能将原始 JSON “翻译”成对 LLM 友好的 Markdown 列表的工具——

summarize_page_state() 函数。

这个任务的本质，是一个树的遍历问题。我们要递归地访问页面结构中的每一个组件节点，然

后按照“- 组件类型 (id: 组件ID)”的格式，把它和它的子节点们打印出来。

这个函数的实现非常直接，我们可以用一个内部的递归辅助函数来轻松搞定。你看，代码实现起来是不是非常简单？

python
def summarize_page_state(page_state: dict) -> str:
   """
   将完整的页面状态JSON，转换为对LLM友好的Markdown格式摘要。
   :param page_state: 代表页面当前状态的JSON对象。
   :return: Markdown格式的字符串摘要。
   """
   if not page_state:
       return "当前页面为空。"
   summary_lines = []
   def _summarize_recursive(component: dict, indent_level: int):
       """递归辅助函数，用于生成每个组件的摘要行。"""
       indent = "  " * indent_level
       component_type = component.get("type", "Unknown")
       component_id = component.get("id", "no-id")
       summary_lines.append(f"{indent}- {component_type} (id: {component_id})")
       if "children" in component and isinstance(component["children"], list):
           for child in component["children"]:
               _summarize_recursive(child, indent_level + 1)
   # 从根节点开始递归
   _summarize_recursive(page_state, 0)
   return "
".join(summary_lines)

第二个模块：编码实现“指令 / 目标”分流器 ​

有了“状态摘要”这个基础工具，我们接下来要构建系统的第一个决策点——“指令 / 目标”分流器（Router）。它的职责就像一个交通警察，快速判断用户的请求是应该走“简单指令”的快速通道，还是应该走“复杂目标”的规划流程。

实现这个 route_request() 函数的核心，就是构造一个轻量级的提示，让 LLM 帮我们做这

个二元选择题。

python
import litellm
def route_request(user_query: str) -> str:
   """
   判断用户请求是“简单指令”还是“复杂目标”。
   :param user_query: 用户的原始输入字符串。
   :return: 'single' 或 'multi'。
   """
   prompt = f"""
请判断以下用户请求，更像是一个可以通过单一步骤完成的“简单指令”，还是一个需要多个步骤才能完成的“复
请只回答 'single' 或 'multi'。
用户请求: "{user_query}"
"""
   try:
       # 这里我们使用litellm来调用大模型，你可以换成任何你熟悉的SDK
       response = litellm.completion(
           model="gpt-3.5-turbo", # 使用一个速度快、成本低的模型即可
           messages=[{"content": prompt, "role": "user"}],
           max_tokens=5,
           temperature=0.0
       )
       result = response.choices[0].message.content.strip().lower()
       if "single" in result:
           return "single"
       elif "multi" in result:
           return "multi"
       else:
           # 如果模型返回了意外的内容，我们默认它为简单指令以求稳定
           return "single"
   except Exception as e:
       print(f"调用LLM进行路由时出错: {e}")
       # 出现异常时，同样默认返回 'single'
       return "single"
# --- 测试分流器 ---
query1 = "把登录按钮的颜色改成红色"
query2 = "帮我创建一个完整的用户注册页面"
print(f"'{query1}' -> {route_request(query1)}")
print(f"'{query2}' -> {route_request(query2)}")
运行这段代码，你会看到它能准确地将两个请求分流：第一个返回 single，第二个返回
multi。这个小小的模块，将为我们的系统节省大量的计算资源，避免了“杀鸡用牛刀”的窘

境。

核心模块：编码实现规划器主类（Planner） ​

现在，万事俱备，我们终于来到了最激动人心的部分——实现我们 Agent 的“大脑”，Planner

类。这个类将是我们上一讲所有设计思想的集大成者。

它的核心方法 generate_plan 将 orchestrate（编排）整个规划流程：获取环境信息、加载

可用工具、动态拼装“终极元提示”，然后调用 LLM 生成计划，并稳健地解析其返回的 JSON。

让我们一步步把这个类构建起来。

python
import json
import litellm
# 我们把上一讲定义的观察工具和这一讲的状态摘要工具放在一起
from observation_tools import get_page_outline
from page_state import summarize_page_state
class Planner:
   def __init__(self):
       # 在实际项目中，工具定义应该从配置文件中加载
       self.tools_definition = self._load_tools_definition()
   def _load_tools_definition(self) -> str:
       """加载并格式化可用的工具清单。"""
       # 为简化起见，我们在这里直接硬编码
       tools = [
           "`find_components(filters: array)`: 根据一个或多个属性条件，查找页面上所有符
           "`createComponent(parentId: string, componentType: string, properties
           "`updateProperty(componentId: string, propertyName: string, propertyV
           "`deleteComponent(componentId: string)`: 删除一个指定的组件。"
       ]
       return "
".join([f"- {tool}" for tool in tools])
   def _build_meta_prompt(self, goal: str, state_summary: str) -> str:
       """
       动态拼装“终极元提示”。这正是我们设计的核心所在！
       """
       # 1. 角色扮演 (Role-Playing)
       role_prompt = "你是一位资深的低代码应用架构师。你的任务是分析用户的需求，并将其分解为
       # 2. 最终目标 (The Goal)
       goal_prompt = f"用户的最终目标是: "{goal}""
       # 3. 环境感知 (Environmental Awareness)
       env_prompt = f"这是当前页面的结构摘要:
```markdown
{state_summary}
```"
       # 4. 可用工具 (Available Tools)
       tools_prompt = f"你可以使用以下工具来操作页面:
{self.tools_definition}"
       # 5. 输出契约与行动纲领 (Output Contract & Principles)
       contract_prompt = '''
你的输出必须是一个严格的JSON格式对象，结构如下:
{
 "plan": [
   {
     "step": <步骤序号>,
     "reasoning": "<你对这一步的思考过程>",
     "tool_name": "<要调用的工具名>",
     "parameters": { <调用工具所需的参数> }
   }
 ]
}
你必须遵守以下行动纲领:
1.  **ReAct原则**: 在决定使用某个工具前，必须先在`reasoning`字段中清晰地写下你的思考过程。
2.  **观察优先**: 在执行任何“修改”类工具（如`createComponent`, `updateProperty`）之前，如
3.  **上下文引用**: 如果一个步骤需要使用前面步骤的执行结果（比如一个新创建组件的ID），你必须使用
4.  **经济原则**: 尽量用最少的步骤完成目标。
'''
       # 将所有部分拼装成一个完整的、巨大的字符串
       full_prompt = f"{role_prompt}
{goal_prompt}
{env_prompt}
{tools_prompt}
{contract_prompt}"
       return full_prompt
   def generate_plan(self, goal: str, page_state: dict) -> dict | None:
       """
       生成行动计划的核心方法。
       """
       # 1. 获取对LLM友好的环境信息
       state_summary = summarize_page_state(page_state)
       # 2. 拼装元提示
       meta_prompt = self._build_meta_prompt(goal, state_summary)
       print("--- 发送给LLM的终极元提示 ---")
       print(meta_prompt)
       print("--------------------------")
       # 3. 调用LLM API
       try:
           response = litellm.completion(
               model="gpt-4o", # 规划任务比较复杂，建议使用更强大的模型
               messages=[{"content": meta_prompt, "role": "user"}],
               response_format={"type": "json_object"}, # 请求JSON输出
               temperature=0.1
           )
           plan_text = response.choices[0].message.content
           # 4. 健壮地解析JSON
           return json.loads(plan_text)
       except json.JSONDecodeError as e:
           print(f"LLM返回的计划不是有效的JSON格式: {e}")
           # 这里可以加入重试逻辑，比如把错误信息告诉LLM让它修复
           return None
       except Exception as e:
           print(f"调用LLM生成计划时出错: {e}")
           return None
请仔细品味 _build_meta_prompt 这个函数。它就像一个精密的装配车间，将我们上一讲

设计的五大要素——角色、目标、环境、工具、规则——程序化地、一丝不苟地组装成最终的“终极元提示”。

同时，注意在 generate_plan 的最后，我们使用了 try-except 来捕获
json.JSONDecodeError。这是非常重要的健壮性处理。LLM 虽然强大，但偶尔也会“犯糊

涂”，返回一些不完全符合 JSON 语法的字符串。一个可靠的系统必须能处理这种情况，而不是直接崩溃。
