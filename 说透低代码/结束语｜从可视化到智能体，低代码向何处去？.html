结束语 | 从可视化到智能体，低代码向何处去？ ​

你好，我是陈旭。这是《说透低代码》的最后一讲。

写下这行字的时候，我特地回去翻了一下专栏的更新记录。这个专栏开写的时候，ChatGPT还没有发布，低代码是编码提效领域当之无愧的主角；写到一半，大模型来了，我们临时调整方向，开始研究低代码如何与 AI 化敌为友；写到现在，端到端的编码智能体已经满大街了，随便一个开发者都能让 AI 替他写完一整个项目。

现在回头看，我自己都有点感慨：这个专栏竟然歪打正着，跨越了研发提效的两个时代——低代码时代和智能化时代。而且不只是见证，我们还在专栏里亲手把这两个时代的核心技术都实现了一遍。

所以，这最后一讲，我想和你做两件事。

第一件事是回顾。我们沿着“两个时代”这条线，把三十多讲的内容串一遍。你不妨把这次回顾当成一次复习，但更重要的是，我希望你能看到散落在各讲里的知识点背后那条一以贯之的主线。

第二件事是展望。这也是我被问得最多、我自己也思考得最多的一个问题：端到端的 Agent 已经能独立完成复杂开发任务了，低代码技术还有未来吗？如果有，它在哪里？

回顾：一个专栏，两个时代 ​

低代码时代：工具箱里只有一件工具 ​

专栏的前 24 讲，我们只做了一件事：围绕低代码编辑器，把一个功能完备的低代码平台从零到一地建了起来。现在回头看，这 24 讲其实是三层。

第一层是认知与策略（开篇词和第 1～5 讲）。

我们从“低代码是银弹还是毒瘤”这个争论开始，把 Pro Code、Low Code、No Code 放在一起比较，最后得出了整个专栏的基石性结论：低代码和纯代码的本质差异，不在于代码量的多少，而在于代码在创造业务价值过程中扮演的角色——对 Pro Code 来说，代码是关键输入；对 Low Code 来说，代码只是中间产物。低代码开发者不需要把业务翻译成一条条指令，他始终在描述和细化业务最终的样子。这就是低代码能提效、能赋能的根本原因。

这一层还有一个我至今都坚持的策略判断：先通用、再具体。通用性创造的是未来的可能性，虽然早期道路坎坷，但路会越走越平坦；反过来，看似务实，路却容易越走越窄。这个判断在当时帮我顶住了压力，后来的事实也证明，它是这个专栏所有技术决策里最重要的一个。

第二层是编辑器的核心技术（第 6～14 讲）。

这是专栏最硬核的部分，我们依次攻克了：代码生成器与编辑器的解耦（那个 Level 1 到Level 4 的抽象分层，现在依然是判断一个低代码平台架构健康度的便捷标尺）、结构化代码生成法、布局编辑器、属性编辑器、可视化编程、Low Code 与 Pro Code 混合开发、业务数据接入、多人协同编辑、编辑历史。这一层解决的问题可以归结为一个：如何用可视化手段，把“布局、交互、数据”这应用开发三部曲的效率做到极致。

第三层是开发能力之外的工程化（第 15～24 讲）。

我们一直在强调一个观点：低代码平台只关注开发能力是远远不够的。于是我们覆盖了应用研发的全生命周期——插件系统与生态、兼容性治理、D2C 设计稿转代码、用三讲的篇幅做应用的自动化测试，最后在第 24 讲，用“开发时、测试时、运行时”三个时态，给这个日渐臃肿的平台做了架构治理。这一讲也是低代码时代的收官。

到这里，如果专栏就此结束，它已经是一个完整的故事了。但是，如果你问我对这个时代最真实的评价是什么，我会说是第 25 讲里的那句话：我们的工具箱里只有可视化一件工具。

这一件工具，决定了低代码时代全部的辉煌和全部的局限。可视化 + 所见即所得，处理描述性任务——界面、布局、数据展示——所向披靡；但一遇到逻辑性任务，它就露怯了：做得简单了不解决实际问题，做得复杂了又背离低门槛的初心。这就是那个困扰了我整整六年的不可能三角：开发效率、易用性、可定制化，三者最多只能拥有其二。

说实话，在大模型出现之前，我以为我这辈子就要和这个三角耗下去了。

大模型闯入：工具箱里多了第二件工具 ​

第 25 讲和第 26 讲是专栏的转折点。

大模型刚来的时候，是以“程咬金”的面目出现的。低代码的输出是代码，大模型也能输出代码，从表面上看，这是赤裸裸的竞对关系。当时几乎所有人都在问：低代码会被 AI 取代吗？

我们的回答是第 25 讲的标题之问，结论现在看依然站得住：大模型不仅不是对手，还是帮手。因为它给我们带来了一样低代码梦寐以求的东西——自然语言。

自然语言这件工具，简直是为弥补可视化的短板量身定做的。它是处理逻辑性任务的合适手段，恰好治可视化搞不定逻辑的病；它可以替代一大批繁琐的可视化配置界面，显著降低平台的开发工作量；它还几乎人人生而具备，没有任何手段比它更契合低代码降低门槛的使命了。

当时我们给出的判断是：与其纠结谁替代谁，不如把两件工具融合起来，各取所长。可视化负责全局观和确定性，自然语言负责灵活表达和复杂逻辑。这两者的组合，将让低代码带着智能化的翅膀再次起飞。

在第 26 讲，我们还做了一个关键的概念区分：Copilot 和 Agent。Copilot 是指令驱动的，人负责拆解任务，AI 负责执行单步指令，人智依然是推动问题解决的关键；Agent 是目标驱动的，你给它一个目标，它自行规划、自行执行，人的职责简化为定义问题、观察和授权。当时我写下了一句话：现在的大模型能力，离实现真正的智能体还有一定距离。

请你记住这句话。因为在第二部分，我们要回过头来好好聊聊它。

智能化时代：亲手造一个 Agent ​

从第 27 讲开始，我们不再纸上谈兵，而是真刀真枪地把一个 Agent 造了出来。这个过程，现在回看，像极了一个数字生命的成长史。

最开始，它只是一个传声筒。一个简陋的 Chatbot，负责把用户的话转述给大模型，再把大模型的话带回来，仅此而已。然后我们教会了它听懂人话：借助 DSPy 做意图分类和实体提取，当用户说“帮我创建一个登录按钮”时，它能识别出意图是 createComponent，并提取出实体componentType: Button。

但能听懂还不够，得能干活。第 29 讲是整个智能化阶段最关键的一次跨越，我们定义了Page Schema 这份页面蓝图，约定了 AI 的能力清单，然后用 JSON Patch 打通了从理解到行动的最后一公里——画布，从此能听懂人话了。紧接着，我们又用意图模板和对话状态教会了它和人类沟通，在信息不全时，它不再摊手说我没听懂，而是会主动追问“按钮上要显示什么文字？”，从一个机械的指令员，进化成了一个懂得协作的伙伴。

不过到这时为止，它依然只是一个 Copilot，一个闭着眼睛开车的执行者。第 31 讲是从Copilot 到 Agent 的决定性一跃：我们为它安装了眼睛，一套只读的观察工具集，让它在行动之前先看清楚画布、先核查事实。从那以后，它的第一反应不再是“我应该做什么”，而是“为了更好地完成任务，我需要先了解什么情况”。

有了眼睛，接下来就是长脑子。我们为它设计了任务规划的思考框架：在入口处用分流器区分简单指令和复杂目标，用包含角色、目标、环境、工具、契约五大要素的元提示引导大模型思考，再用 $steps 引用语法解决计划步骤之间的依赖。于是，创建一个登录表单这样的复杂目标，第一次被拆解成了一份逻辑严密的行动计划。然后，执行引擎给大脑接上了四肢，让计划真正动了起来；最后，我们又教会了它反思——失败不再意味着崩溃，而是被捕获、被分析、被重规划，一次硬错误甚至可以被优雅地转化成一次与用户的智能交互。

至此，观察 - 规划 - 执行 - 反思的完整闭环形成。我们的 Agent 能看、能想、能干，还打不垮。

两个时代，不变的到底是什么？ ​

回顾完了。在合上这本相册之前，我想请你和我一起，做最后一次提炼。

这两个时代，技术栈天差地别，但有两样东西从头到尾没有变过。

第一，目标没有变。无论是用可视化替代编码，还是用自然语言驱动画布，我们做的事情始终是同一件：降低软件开发的门槛，提升业务交付的效率，赋能更多人参与业务创造。技术一直在换，这个目标一天都没有变过。

第二，矛盾没有变。两个时代面对的其实是同一个矛盾的两种形态：确定性与灵活性的张力。可视化赢在了确定性和全局观，输给了灵活性；自然语言赢在了灵活性和低门槛，输给了确定性和精确性。这个专栏从头到尾所有的架构决策，本质上都是在这一对矛盾里寻找平衡点。

那么变的是什么？只有工具。我们的工具箱，从只有可视化一件工具，变成了可视化加自然语言两件工具。

我还想说一个可能容易被忽略的细节。低代码时代的那些架构投入——Page Schema 让“页面即数据”，平台能力的工具化让读写操作都有清晰的契约——在当时是为了解决低代码自身的问题而做的。但谁能想到，恰恰是这些投入，成了智能化时代最好的地基：Agent 需要的“眼睛”，就是对 Page Schema 的结构化读取；Agent 需要的“手”，就是那套工具化的平台能力契约。

你看，先通用、再具体，通用性创造的是未来的可能性。这句话在智能化时代，又被验证了一次。

展望：端到端 Agent 时代，低代码向何处去？ ​

好了，现在我们来聊那个最扎心的问题。

先承认现实：这一次，真的不一样 ​

在专栏的第二部分开始前，我要先做一次自我批评。

第 26 讲里我写下的那句“大模型能力离实现 Agent 还有一定距离”，在当时是对的。但老实说，我没有预料到，这个距离会被压缩得这么快。才过了短短一两年，端到端的编码 Agent 已经从实验室里的稀罕物，变成了满大街的日用品。这些解决方案主打的就是端到端完成复杂任务，过程人类无需介入。

更值得我们这些低代码人警觉的是：UI 构建曾经是 AI 表现最差的领域。界面上的细节，像素级的调整，风格的协调，过去都需要人给出非常详细的提示，AI 才能勉强完成。而这个领域，恰恰是低代码的主场，是我们这个专栏三十多讲的主战场。可现在，连这个最后的堡垒也在被快速攻克——随手截一张设计稿丢给 Agent，它生成的界面已经像模像样了。

所以，我们就直面那个问题：如果 Agent 一句话就能端到端生成一个应用，我们专栏讲的这些——编译器、编辑器、Page Schema——还有意义吗？低代码技术，会不会像当年它挑战 ProCode 一样，被新的方式拍在沙滩上？

我的答案是：低代码的“形态”一定会变，但低代码的“内核”不但不会死，反而会成为 Agent 时代最重要的基础设施之一。下面我展开讲。

想清楚：Agent 到底替代了什么，替代不了什么？ ​

要回答上面的问题，我们得先把 Agent 做的事拆开看。

Agent 真正替代的，是代码和界面的生产过程。敲代码、拖组件、填配置表单，这些生产动作的成本，正在以肉眼可见的速度趋近于零。这一点我们必须承认，而且承认得理直气壮：因为低代码当年崛起，靠的也是压缩生产过程的成本，只不过我们把成本压到了拖拽配置的水平，而 Agent 把它压到了“一句话”的水平。这是同一条路，只是 Agent 走得更远。

但是，生成一个应用，和养活一个应用，是两回事。Agent 替代不了的，恰恰是这个专栏第三部分反复强调的、那些开发能力之外的东西。

第一是确定性与可控性。Agent 本质上是概率性的，同一个提示，今天和明天生成的结果可能都不一样。而企业级业务要的是可预期、可复现、可审计。一个支付页面的行为，不能“大概是对的”；一个审批流程的权限，不能“应该没问题”。确定性从哪来？从结构化的描述、强约束的契约、可验证的生成过程来，这些正是低代码技术的内核。

第二是私域知识与业务资产。通用 Agent 不懂你的业务。它不知道你们公司的“客户分群”有七层定义，不知道你们的审批流要过三道合规检查。而低代码平台多年沉淀下来的东西——组件集、业务模板、数据模型、插件生态——正是这些私域知识的载体。在 Agent 时代，这些资产不但不会贬值，反而会因为成为喂给 Agent 的弹药而升值。

第三是全生命周期的工程化。第 24 讲的三时态还记得吗？开发、测试、运行。Agent 目前擅长的主要是开发时，但一个真实的业务应用，还要过测试、灰度、上线、监控、回滚，还要多人协作、权限管控、合规审计。生成一个应用只要一句话，养活一个应用要三年五年。这条全生命周期，是低代码平台用十几年时间铺好的路，Agent 自己可不会长出来。

第四是长期演进与维护。一次性生成是容易的，但业务是活的，它要持续演进三五年。当Agent 生成的几十万行自由代码需要修改时，谁来保证改得动、改得安全？结构化的底座——页面即数据、组件即契约——决定了一个应用能不能被持续、安全地演进。

所以你看，Agent 把生产变廉价了，反而让生产资料和生产关系变得前所未有地值钱。而这两样，都是低代码的家底。

低代码技术的三个去向 ​

分析到这里，低代码技术的未来图景其实已经浮出水面了。我把它归纳成三个去向，前两个我有比较大的把握，第三个，我坦白说，我也还在观察。

去向一：从人的 IDE，变成 Agent 的工具箱和运行时。

以前，低代码平台的服务对象是人，所以它的交互界面是给人用的拖拽画布。未来，它的主要服务对象会变成 Agent，Agent 通过结构化的契约来观察页面、操作组件、执行变更，PageSchema 从渲染的唯一真实来源升级为人机共用的接口。

其实，我们在第 31 到 35 讲已经提前演示过这个方向了，你可以回去翻翻：当时我们手写了观察工具集、规划器和执行引擎，让 Agent 操作画布。未来唯一的变化是，驱动这些工具的，不再是我们自己写的那个朴素的规划器，而是能力强得多的通用 Agent。平台能力工具化、契约化，就是低代码平台在 Agent 时代的入场券。如果你有平台，这件事现在就值得做。

去向二：可视化不退场，但角色变了——从生产界面变成审核与微调界面。

人的角色，正在从操作者变成验收者、授权者。但请注意，验收和授权也是需要界面的。当Agent 生成了一个页面，你要怎么审查它？读代码吗？不，最高效的方式依然是所见即所得地“看”它，然后动手微调那最后 10% 的细节。

所以第 29 讲那个“自然语言负责 0 到 1，可视化负责 1 到 1.1”的判断，在 Agent 时代依然成立，只是 0 到 1 的执行者，从 Copilot 换成了端到端的 Agent。可视化从生产的舞台中央退到了审核和精调的岗位，但这个岗位，依然无可替代。你很难想象用语言精确描述“把这个按钮向右移 13 像素，再调成饱和度低一点的蓝色”，但用鼠标，那是几秒钟的事。

去向三：不可能三角可能被打破，但低代码的“形态”未必还在。

这个去向，我承认我还没完全想好，我给你看两种可能。

第一种可能：低代码平台进化为 Agent 驱动的业务生成平台。Agent 提供可定制化，自然语言提供低门槛，可视化提供确定性，那个折磨了我六年的不可能三角，居然在三件工具的合力下有可能被打破。低代码平台以一个新的形态，兑现它当年的承诺。

第二种可能：低代码作为独立的产品形态逐渐消解，但它的技术内核——结构化描述、代码生成、轻量运行时——融入 Agent 的基础设施，变得无处不在，又隐形不见。就像编译器技术从来没有消失，只是普通人再也看不见它了。

哪一种会成真？我不知道，可能两者会同时发生在不同的领域。但我确定的是，无论哪一种成真，我们在第 26 讲说过的那句话都不会错：与其到最后被碾压和抛弃，还不如现在就将它作为己用。打不过，就加入。

给读者的三条建议 ​

老规矩，咱这是个务实的专栏，最后给你三条可以马上动手的建议。

  • 如果你手里有一个成熟的低代码平台：请加速做两件事，一是把平台能力工具化、契约化，让它能被 Agent 调用；二是死死守住资产层（组件、模板、数据模型）和工程化层（全生命周期能力）这两块护城河。未来你的平台价值，不再取决于画布做得多炫，而取决于它对Agent 有多友好、它的资产有多厚。

  • 如果你刚起步：那就不要再去从零造一个可视化编辑器了，那个时代的窗口已经关上了。围绕“Agent + 结构化契约”来设计你的产品，把可视化当成审核层而不是生产层。

  • 对你个人：请放心，低代码这些年训练出来的能力——业务抽象、结构化描述、全生命周期视角——恰恰是 Agent 时代最稀缺的能力。Agent 越强，越需要能驾驭它的人。知道怎么把业务讲清楚、知道怎么判断结果对不对、知道应用的一生要经历什么的人，比会写代码的人更稀缺。你不是被时代抛下的人，你是早就在为这个新时代做准备的人。

写在最后 ​

在专栏的开头，我们一起讨论过一个问题：低代码是银弹吗？第 25 讲的结尾，我们又回答过一次：是。今天，在专栏的最后，我想第三次、也是最后一次回答这个问题。

低代码是银弹吗？不是。Agent 是银弹吗？也不是。回头看这两个时代，从来就没有什么银弹。如果说真有什么东西配得上“银弹”这两个字，那它不是任何一种技术，而是那个贯穿始终的追求本身，让软件开发这件事，门槛更低一点，效率更高一点，参与的人更多一点。低代码是这个追求在上一个时代的答案，Agent 是这个时代的答案，未来还会有新的答案。技术会老去，但这个追求不会。

最后，我还想再说一次 Awade 这个名字的故事。它来自 “Anyone can be A Web ApplicationDeveloper Expert”——人人都是 Web 应用开发专家。这是我们当年做低代码平台的初心。说心里话，写下这句话的时候，我以为这个使命要靠可视化编辑器来实现。谁能想到，短短几年之后，它正在以一种我们当年完全没想到的方式，通过说自然语言就可以变成现实。

从这个意义上说，低代码没有输。它的使命，正在被接棒实现。

谢谢你，陪我走完这三十多讲、跨越了两个时代的长跑。这一路，我们从拖拽组件写到反思型智能体，从银弹之争写到人机共生，我很庆幸，我们没有辜负这个波澜壮阔的时代。

低代码之路，我们才刚刚开始。现在回头看，这句话依然正确，只不过路的前方，已经从低代码，延伸向了更辽阔的智能化旷野。

我是陈旭，山高路远，我们江湖再见！
