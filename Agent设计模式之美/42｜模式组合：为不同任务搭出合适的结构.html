42 | 模式组合：为不同任务搭出合适的结构 ​

  • 释题：因事制宜。同样几种模式，可以搭出不同的工作方式。怎样连接，要看这件事需要什么材料、哪些步骤互相依赖，以及做错以后会有什么后果。

你好，我是黄佳。

上一讲，我们从退款助手出发，讨论了什么时候用普通程序，什么时候值得让模型参与。现在，你也许已经能为一个具体问题选出模式。接下来却还有一个问题：选出的几种模式，怎样组成一套系统？

假设你在公司里接到三项任务。

  • 第一项，比较三个地区的退货政策，交一份有出处的说明。

  • 第二项，排查升级后出现的接口错误，修好以后提交代码。

  • 第三项，根据业务人员的要求，为新部门配置薪资组。

这些任务既有相似性，也有差异，都要查资料，都可能需要推理，也都可以加评审。可如果把它们一律写成“检索、生成、评审、执行”，那就太僵化了。

三个地区的资料，可以并行调查。排查接口时，却经常要看完一条日志，才能决定下一步查什么。薪资组一旦开始导入，程序还必须知道哪些准备已经完成，有时需要重新规划，还要保存之前的进度。

模式组合要设计的，正是这些配合关系。我们既要决定每部分负责什么，也要决定谁等谁、谁能修改什么、出了问题回到哪一步。

而七组模式，是观察系统的几个角度，可以沿着一项任务重新串起来看。

  • 感知帮助我们拿到当前需要的材料，记忆让已经查过的事实和做过的工作能够留下来。推理根据这些材料决定下一步，行动把决定落实到工具。反思检查结果，必要时修正。工作需要交给不同参与者时，用协作模式安排分工。涉及权限、影响范围和责任时，再由治理约束这些活动。

我们并不要求每一项任务都覆盖七组模式。调查中的一次工具调用，可能同时涉及推理、行动和治理。进度记录则会被多处读取，也会随着任务不断更新。一套系统可以同时包含各种拓扑结构。比如外层按顺序完成调查、写作和发布，调查内部可以并行，每个调查分支又可以继续搜索。

《Designing AI Agents》把组合设计分成三个问题：模式能否处理任务中的困难，相邻模式能否配合，整套设计能否满足实际使用要求。上一讲主要回答第一个问题，这一讲重点看后两个。

下面就从这三项典型的任务出发，思考每次安排背后的理由。以后换成新的业务需求，你仍然可以用同样的方法作判断，在不同模式之间组合，以适配各种不同场景。

任务一 资料研究：先分头查，再共同核对 ​

业务同事要你帮忙比较三个地区的退货政策。如果你已经有三份有效文件，而且一次调用就能完整比较，先把文件交给模型即可。这种简单情况，没必要引入协作，让三个 Agent 各读一页。

但现在把条件改一下。文件散落在多个站点，有修订通知，还有一些例外条款。一个地区的材料已经进入知识库，另一个地区需要继续追查原始发布页。此时，调查工作明显变多了。

这时就可以按地区拆开。每一路都回答相同的问题：适用什么商品、退货期限多长、有哪些例外、规定从什么时候生效。分支交回结论，也交回出处。汇总者收到三份材料以后，再按这些项目比较。

这里用到了扇出聚合模式。三路分别工作，最后检查资料是否到齐、能否放在一起比较。

每一路内部又可以采用不同办法。已有整理好的文档，就用检索增强查找相关段落。发现一条修订说明指向另一份文件，就用渐进发现继续找，直到把当前结论需要的依据补齐。也就是说，扇出的每一条链路上都可以有属于自己的具体模式。

  • 三路调查可以并行。起草使用整理后的材料，评审核对具体结论时仍能取回原文。

假设甲地区的原文写着：“支持七天退货，定制商品除外。”调查分支交回的摘要却只保留了“支持七天退货”。报告据此写成：“甲地区所有商品都支持七天退货。”如果后面的评审只看报告和摘要，它手里没有那句被漏掉的例外信息，再认真也不容易发现。

所以，语义压缩和生成评审放在一起时，需要给评审保留另一条取证路径。摘要帮助写作者快速了解材料，原文位置帮助评审者核对具体结论。评审发现疑问，再取回相应段落，不必每次重读全部文件。

这就是组合以后多出来的设计：单看压缩，我们可能只关心缩短了多少。单看评审，我们可能只关心评分标准。把两者放在一起，才会发现评审者可能已经失去了发现错误所需的材料。

如果问题变成“研究公司进入某个市场需要面对哪些障碍”，连调查方向都要边查边决定，才更值得采用层级委派模式：由主 Agent 拆出法规、渠道、产品适配等子任务，并根据返回结果补充调查。层级委派安排责任，扇出聚合安排多个分支怎样展开和收回，两者可以共用同一套调度实现。

至于对抗评审，如果眼前的争议只是两份材料生效日期或者证据细节不同，只要把日期、资料来源查清就好。只有当证据已经摆齐，发现仍需要不同专业立场检查结论时，增加不同评审角色才更有意义。

任务二 故障排查：先让证据决定调查，再组织修改 ​

再看第二项任务：“依赖升级以后，接口测试失败了，请排查并修复。”

这个任务和资料比较有不同之处，因为随着证据的发现和调查的展开，排查过程也要逐渐发生变化。

开始时，我们通常无法一次性列好所有调查步骤。发现版本差异以后，可能会怀疑配置。读完配置后，可能发现其实是某个返回字段的类型改变导致了接口报错。如果上来就编排成“先查依赖、再查配置、最后查业务代码”这三步固定流程，不但浪费时间，还可能把真正需要追查的线索挤到后面。

因此，设计阶段我们先保留一个调查循环：提出可能原因，选择能够区分这些原因的检查，读取结果，再决定下一步。这就是迭代假设验证的应用。渐进发现则可以帮 Agent 寻找文件、调用方和日志。这两种模式分别负责处理“去哪找材料”和“这份材料支持哪个解释”。

例如，Agent 怀疑连接超时，查日志却发现请求很快就返回了，只是响应里少了一个字段。下一步应当检查响应格式与调用方，不该继续增大超时参数。也就是说，调查顺序应该接受证据的影响，由模型来动态地进行。

假设最终确认：升级改变了返回格式，需要修改适配器，补上回归测试，再更新两处调用代码。

这时已经能够列出有依赖的改动，可以采用规划执行模式保存计划，由执行器安排可开始的步骤。前面的调查仍然灵活，后面的改动则有可检查的次序。

如果只是把一个已经确认的字段名改正，直接修改并测试就够了。改动之间确有依赖、需要中断续做或调整安排时，再保存计划。

  • 调查根据新证据转向。修复方案明确后执行改动，再检查结果。测试失败要判断失败原因，不能无限重试。

测试又失败了，可以怎样处理？

如果是修复中的一个局部错误，允许自愈循环再修改、再测试。如果结果推翻了原先的判断，就应回到调查，而不是要求修复器沿着错误原因继续改。若超过本次允许的尝试次数或时间，就停下来，把改过的文件和失败结果交给工程师。

这里要注意到反复尝试时的 Token 消耗，如果外层调查允许三轮，内层每轮又自动修复五次，实际就可能运行十五次。组合时必须有一个任务级预算，内部循环也需要分别给每个组件设置上限，否则仍可能让整个任务拖得很长。

下面我们继续探讨评审、审批和记忆怎样接入这个任务。

生成评审检查这版修改是否符合原要求。它需要看到代码差异、相关测试和约束。例如，删掉权限检查也许能让某条测试不再报错，却破坏了系统原本的行为。

审批门则决定能否把这份修改提交到受保护的分支，或发布到生产环境。允许 Agent 在隔离副本里试改，人工确认可以放在真正需要承担外部后果的位置。

进度追踪保存已排除的原因、当前改动和测试结果。任务暂停后，下一次能够从中断处继续。修复结束以后，有复用价值的失败过程可以进入失败日志。如果希望把这次的补丁沉淀为通用技能，需要在其他样例上验证，明确适用条件，可以考虑整理成技能包。

若要并行排查，可以让几个 Agent 分头调查原因，汇总后由一个执行者改代码，架构上先避免多人同时修改同一接口。确实需要并行写入时，再单独设计文件分工和冲突处理。

任务三 业务办理：灵活理解，按依赖执行 ​

本课的最后一个任务，我们来重温这个熟悉的案例——企业薪资发放 SaaS 实践。具体任务是：参考现有配置，为新部门建一套薪资组，补贴规则有所不同，旧配置不能被破坏。

从模式组合使用的角度分析，有两类工作要完成。

  • 模型需要理解业务人员描述的差异，寻找候选模板，必要时追问。

  • 模板确定以后，创建备份、导入配置、查询结果这些步骤，却有严格依赖。

梁博团队的实践就遇到过这类问题：当他们把操作次序写进 Skill，再让模型逐步选工具，测试中仍会出现跨步和漏步。后来团队的选择是把已明确的依赖交给任务图和调度器管理，探索部分保留灵活性。

沿这个思路来设计，模型探索并提出方案，规划执行管理计划和依赖。需要审批的写入先取得批准，范围限制和前后检查落实在实际调用处。下面的图展示了这些安排怎样配合。

  • 探索确定方案，执行器管理依赖

规划执行和工具调度，有不同的责任。计划写明步骤依赖，执行器按完成状态推进，备份成功后才能导入。工具调度再核对当前状态和权限，决定这次调用能否获准。流程上轮到了，不等于此刻就有权执行。

如果整项任务永远只有一套固定步骤，普通工作流仍然合适。需要根据企业情况形成不同方案、增加节点或局部调整，才更能体现规划执行的价值。

下面我们继续来看批准、限额和护栏怎样配合起来。

审批门判断这项变更能否执行、是否需要人确认。爆炸半径控制约束这次获准操作最多影响哪些部门、多少对象。护栏三明治在调用前检查条件，调用后核对实际结果。它们可以保护同一次导入，却不能互相代替。人批准了一个部门的配置，不等于程序可以顺带覆盖其他部门。范围没有超出，也不说明配置内容一定正确。导入接口返回成功，还要查询目标薪资组，确认它确实采用了选定配置。

这三种模式并不一定要设计成三个微服务。它们可以在同一个业务入口内调用同一份策略和当前数据，最后共同决定是否继续。如果任何一项必要条件没有满足，写操作就不能执行。

另一个问题是：交接链模式在这个场景中需不需要出现，又如何实现。

如果同一程序从头办到底，保存任务状态即可。不必把每次函数调用都叫作一次 Agent 交接。当配置工作交给实施 Agent，核对工作交给财务 Agent，双方的上下文、工具权限和责任不同，交接链才有明确的用处。接手者需要知道要处理哪家企业、哪版配置，上一方做到了哪里，自己还要完成什么，以及交接之后由谁负责继续。

同时，流程要区分“等审批”和“执行失败”。前者保存任务、等待有权限的人决定。后者根据失败结果判断能否恢复、是否需要重新规划。前面我们提到的自愈循环模式是对真实失败的LOOP 工程，但我们要注意它是否在反复尝试绕过需要人工审批的环节。

等系统积累了足够的运行证据，再用渐进承诺讨论哪些低风险变更可以减少人工确认，并据此调整后续允许 Agent 自动做多大范围的任务。

从三个场景里，找到归纳组合的方法 ​

到这里，我们已经用了不少模式。回头看，每次增加都有不同的原因：资料研究要扩大调查范围，故障排查要跟随证据转向，业务办理要在明确条件下改变系统。

因此，即使业务名称相同，工作方式也可能差很多。更有用的是把组合关系分清。

  • 有些关系是前后供料。检索给写作提供原文，生成评审给修订提供问题和依据。要确认下一步拿到的是它真正需要的材料，而不仅是一个格式合法的结果。

  • 有些关系是内部嵌套。资料比较可以外层并行、内部继续搜索。代码修复可以外层执行计划、局部失败后再试。预算和完成条件要由整体任务管理，不能让每个小循环各自宣布“还可以继续”。

  • 有些关系是执行约束。审批和范围控制作用于真正的写入。它们不一定是主流程上依次走过的两个方框，可能是每次动手前都要满足的条件。

  • 还有些能力由多个步骤共享。规划器、执行器和接手者读取同一份进度，避免各存一份互相冲突的状态。可观测性记录各处发生的事情，方便找到是哪一次查询、修改或判断出了问题。

这些关系可以直接落实成函数调用、队列、状态机和持久化记录。模式带给我们的是设计和架构的思路；而服务数量、模型数量或部署方式则依据项目情况各有不同。

  • 组合可以改变前后顺序、并行范围和反馈位置。权限与记录也可以贯穿多步，不必全部排成一条长链

如果用任务、状态、权限和证据四条线来检查组合，需要思考后面这些问题。

  • 任务有没有走偏？原本要比较三地政策，是否最后只交了两地资料，却没有说明缺哪一地？

  • 事实还能不能追到出处？评审看到的摘要，能否找回那句被删掉的例外？

  • 后续动作还在允许范围内吗？计划重新安排了步骤，是否顺带扩大了原来获准修改的部门？

  • 完成以后拿什么验收？代码测试是否仍覆盖原要求，配置是否已经进入目标业务系统？

检查到哪一步，应当取决于后果。调查员临时换一个搜索词，不需要重审全部任务。改了最终结论的依据，或者换了准备写入的对象，就会影响后面的判断，必须让相关环节知道。

这也是我不主张把每一次内部思考都固定成复杂接口的原因。留给 Agent 的自由，应当用在那些确实需要探索的地方。而明确的业务身份、操作权限和最终验收，则由系统保存和检查。

模式组合有用，但还要从整体上看全局任务 ​

前面的设计都说得通，也仍然可能不值得采用。

三个地区只各有一份短文件时，拆成三个 Agent 再汇总，可能比一次处理更慢。生成评审发现的错误很少，却让普通咨询多等很久，也未必划算。长任务的进度记录虽然增加一些实现成本，却可能省掉中断后反复调查的时间。

比较时，要让两种方案处理同一批任务。资料研究看关键结论和出处是否正确、有没有遗漏。代码维护看目标问题是否解决、原有行为有没有被破坏。业务办理看系统最终改变了什么、有没有越权或重复执行。然后再看时间、费用和人工接手的工作量。

不能因为某一个组件的分数变高，就认为整套设计更好。例如评审提高了报告准确率，却让一项需要即时答复的业务等上几分钟，这个组合仍然需要调整。

因此，一张有用的组合图旁边，最好还有一段说明：为什么需要这些部分，为什么按这个顺序连接，出现什么结果时准备撤掉其中一层。此时，下一位维护者才能理解当初的取舍。

总结一下 ​

面对不同任务，我们可以采用不同组合。资料研究让独立方向并行展开，同时保留原文供核对。故障排查让新证据影响下一步，原因确定以后，再组织修改和测试。业务办理把灵活的理解与严格的执行条件接起来，保证计划能够安全地变成实际操作。

模式名称帮助我们看见这些选择。真正落到设计上，还要回答：下一步需要什么，谁有权继续，失败时退回哪里，最终怎样知道事情办成了。

你可以拿自己的一项任务画一张图。先画业务活动，再在需要的位置标上模式名称。哪一条连线解释不清，就从那里继续设计。图上没有填满的地方，也许普通程序就已经足够。

思考题 ​

  1. 从你的系统中找两个可以分别运行的部分。它们是否也能独立作决定，还是必须等对方提供某条事实？这会怎样影响并行安排？

  2. 选一条“检索、压缩、生成、评审”的路径。如果压缩漏掉了一个例外，评审从哪里能把它找回来？

  3. 你的系统里哪一层是为了改善质量而增加的？用什么结果，才能判断它值得保留，而不只是让架构图更完整？

下一讲预告 ​

系统上线以后，原来的检查可能漏掉了关键业务条件，工具可能越来越重复，模型升级也可能改变某道评审的作用。原来的安排还合不合适，需要重新检查。

最后一讲，我们回到真实架构的变化过程，讨论哪些证据足以支持保留、修复、重组或简化一项设计。整门课最终要帮助你判断的是：现在该改哪里，为什么这样改，又怎样确认改对了。
