33 | 扇出聚合：让多路证据保留差异再汇成结论 ​

  • 释题：让多路证据保留差异再汇成结论。扇出扩大搜索面，聚合器负责盘点缺席、对齐口径、保留冲突和追踪来源，再把材料交给业务裁决。

你好，我是黄佳。

上一讲，我们把一页技术简报拆成了三个不同的责任。Atlas 研究协作拓扑，Birch 研究状态管理，Comet 研究跨 Agent 交接。这解决了各个子代理分工不清晰的问题。结果收回来的时候，主编问：“DeepSeek Harness 的子 Agent 是隔离的吗？”

三个人的回答如下。

  • Atlas 说，会话上下文是隔离的。

  • Birch 说，进程内 Worker 仍可能看到同一个工作区。

  • Comet 说，工具列表可以受限。

这三句话其实聚焦在不同的维度，第一句讨论会话边界，第二句讨论文件系统边界，第三句讨论工具权限边界。如果主编（也就是主 Agent）不保留这些维度，而是把三张资料卡统一压缩

成“隔离”或者“不隔离”。其中两张没有出现 shared，于是系统会按两票对一票给出结论：

DeepSeek Harness 的子 Agent 默认完全隔离。

上面这个例子主要是为了告诉我们，在聚合阶段可能会出现的新问题是：各种带限定条件的证据，有可能在聚合过程中被压缩成片面的、不能区分其推论背景的选票。

模拟聚合失败的一个案例 ​

我们进入公开 Repo，运行下面的命令。

bash
（配套实验：collaboration/light_labs/editorial_gather_lab.py配套工作台：
collaboration/light_labs/web_app.py）
git clone https://github.com/huangjia2019/agent-design-patterns.git
cd agent-design-patterns
python3 collaboration/light_labs/editorial_gather_lab.py
第一次的输出中，聚合器采用了最省事的办法。凡是没有明确写 shared 的答案，都算作支

持隔离。

== flatten and vote ==
answer=isolated support=2/3
lost=workspace:shared
三张投票卡中确实有两张被归到了 isolated 一侧。问题在于，三位研究员并没有围绕同一

个字段投票。

session：
  • 彼此是否看到相同的会话上下文？
workspace：
  • 彼此是否访问相同的工作目录和文件？
tools：
  • 彼此是否拥有相同的工具集合？

把三个字段折叠成一个布尔值以后，多数票失去了统计意义。

在第二次输出中，聚合器不急着选择“隔离”或“不隔离”，它先保留每张卡的维度和来源，按维度收回每一张证据卡：

== evidence-aware gather ==
verdict=qualified admitted=true
session   boundary=isolated   source=dsh subagent docs
workspace boundary=shared     source=dsh spawn provider
tools     boundary=restricted source=dsh tool filter
risk=workspace_shared
这一次的最终结论是 qualified，也就是“有条件成立”。
此时的准确的表述是：进程内 spawn Worker 拥有独立会话，工具面可以受到限制；文件系统

是否隔离，则取决于 provider、沙箱和运行策略。

实际上，session=isolated 与 workspace=shared 并不冲突。它们描述的是两种不同

边界。前一个实验中聚合器的错误主要在于删掉了证据所属的维度。

也可以启动网页版工作台进行观察：

python3 collaboration/light_labs/web_app.py

浏览器打开 http://127.0.0.1:8098，左侧选择“33 扇出聚合”，点击“运行对照实验”。工作台会顺

序执行 flatten_and_vote() 与 gather()。

上面已经解释过，左侧的 2/3 错在把三个不同问题当成同一张选票。右侧把 session、
workspace 和 tools 三张卡按原维度收回，所以结论是 qualified，并且要把
workspace_shared 这个信息交给下游判断。

这个小实验揭示了：聚合过程中收回来，不等于拼起来。

扇出聚合的工程化定义 ​

扇出聚合并不是大模型时代才出现的结构。

2004 年，Jeffrey Dean 与 Sanjay Ghemawat 发表 MapReduce。Map 阶段处理输入分片，Reduce 阶段按照键合并中间结果，运行时负责切分、调度、通信和故障恢复。

今天许多 Agent 并行架构仍然沿用这副骨架：

  • 输入分片
 ↓
并行 Worker
 ↓
  • 中间工件
 ↓
  • 聚合函数

Agent 系统比数值计算多了一层语义问题。因为两个整数可以直接求和，两份调查结果却可能讨论不同对象、不同时间、不同单位和不同来源。即使文本看起来相似，也未必能放进同一个Reduce。

MapReduce 留给 Agent 工程最重要的启发，不是“尽量并行”，而是把执行函数与收口函数分开设计。Map 负责局部计算，Reduce 必须事先说明怎样对齐、怎样组合、怎样处理缺席和异常。统计学习中的 Bagging 则提供了另一条参考。多个基学习器在不同样本上训练，再通过平均或投票降低方差。它能够发挥作用，一个重要前提是基学习器之间存在差异。

如果多个 Worker 使用同一模型、同一提示、同一资料和同一搜索顺序，它们很可能共享同一盲区。输出数量增加了，独立证据没有增加。三份同源判断，不会因为来自三个会话就自动成为三份独立证据。

我们的设计模式双轴框架中，扇出聚合放在“协作 × 并行”坐标。

它的一次完整运行有三段：

  1. 把能够独立推进的工作扇给多位 Worker。

  2. 每位 Worker 在相对隔离的上下文中形成小工件。

  3. 聚合器按明确规则对齐、去重、保留冲突，再形成一份总结果。

扇出聚合的工程化定义如下：扇出聚合把一个具有真实并行面的任务分发给多个独立执行者，再由聚合器依据覆盖、口径、冲突和来源规则，把局部工件收成一份可以继续裁决的结果。

“可以继续裁决”几个字很重要。聚合器不一定替业务做最终决定。它首先要让上层看清：哪些证据到齐了，哪些相互冲突，哪些来源缺席，最后那句结论从哪几张卡推出来。

为什么值得用扇出聚合 ​

扇出聚合的第一个收益是缩短墙钟时间。

假设三个调查方向分别需要 12 分钟、8 分钟和 10 分钟。串行执行的理论耗时约为 30 分钟；并行执行以后，主体耗时更接近最慢的一路，再加上调度和聚合开销。对于网页检索、代码扫描、合同初筛、区域数据核验这类等待时间较长、分片之间依赖较少的任务，并行带来的时间收益是非常明显的。

第二个收益是扩大证据面。

不同 Worker 可以访问不同来源，使用不同工具，或者从不同专业角度检查同一个对象。安全Agent 查看漏洞库，代码 Agent 读取调用路径，运维 Agent 检查运行配置。三路结果合在一起，比单一路径更容易暴露盲区。我们也已经反复强调了，证据面扩大并不等于简单增加票数，聚合器需要同时保留结论和来源血缘。

第三个收益是把局部失败显式化。

如果八个 Worker 分别处理八百份合同中的八个批次，最终只回来七份，聚合器应该报告缺少哪一批，而不是把七份高质量报告拼成一份看起来完整的总结。类型化聚合能够把缺席、超时、坏格式和冲突保留在报告中，系统才有机会选择等待、重派、降级或交给人工。

这些收益都伴随成本。并行会增加 token、连接数、速率限制、调度、重试和聚合开销。任务没有真实并行面时，扇出不会带来收益；结果没有统一工件结构时，聚合器还会成为新的上下文瓶颈。

这也帮我们区分开了层级委派、扇出聚合与并行探索这三个相近模式。它们都可能在图上出现多条并行分支，处理的却是不同问题。

  • 层级委派强调责任划分。例如，一位 Worker 负责状态，一位负责拓扑，一位负责交接。主管首先要检查三块责任是否全部完成。

  • 扇出聚合强调多路结果的收回。例如，三位 Worker 同时调查同一套系统的会话、工作区和工具边界。聚合器要保证三张卡仍然保持原来的维度，不能把不同口径压成一张选票。

  • 并行探索强调候选解法。例如，同一道代码修复题同时尝试三条补丁路径，再依据测试结果选择一条继续推进。它关注的是候选路径竞争，而不是证据分片的完整收回。

真实系统经常组合这些模式。Lead Agent 可以先按地区做层级委派，每个地区 Worker 再对多个资料源进行扇出聚合；聚合过程中若遇到未决问题，还可以启动并行探索比较多种解释。

对象一致性，所有 Worker 是否在讨论同一个对象？

“Claude Managed Agents”“Claude Code subagent”和某个自建 Agent wrapper，名称接近，运行边界却可能完全不同。对象应绑定产品、provider、部署方式或实体 ID，而不是只靠自然语言名称匹配。

时间一致性，证据是否来自允许比较的时间范围？

一个 Worker 使用 2026 年 8 月的文档，另一个引用 2025 年旧版实现，结论不同可能只是版

本变化。聚合器应保留 observed_at、版本号或 commit。

单位和口径一致，金额、比例、币种、统计周期和分母是否一致？

38,444 与 384.44 可能相差一百倍，也可能只是分与元的换算。10% failure rate 可

能按调用计算，也可能按任务计算。归一化之前不能直接加总或比较。

来源可追溯：每张卡能否回到具体文档、查询、代码位置或数据快照？

“根据官方资料”不是稳定引用。聚合结果需要保留来源 ID、版本、访问时间和必要的内容摘要。

置信语义一致，不同 Worker 返回的 0.8 是否表示同一种东西？

它可能是模型主观把握、分类器概率、规则命中率，也可能是经过校准的统计概率。字段名称相同，不代表数值具有相同语义。

聚合器依次做五件事 ​

“聚合”听上去像一个动作，但工程上把它按顺序拆解开，主要有下面五个步骤：

第一步：盘点缺席

聚合开始时，先检查应该返回的工件是否全部出现。

本讲要求 session、workspace 和 tools 三个维度各有一张证据卡。只要缺少一个维度，
报告就应进入 insufficient，而不是让主 Agent 依据常识补写一段。

合同处理、简历筛选和数据核验中，缺席通常通过分片 ID 识别：

expected_shards = {A, B, C, D}
received_shards = {A, B, D}
missing_shards  = {C}

缺失分片必须进入结果状态、监控和重派流程。成功结果的数量不能掩盖未处理输入。

第二步：归一口径

结果到齐以后，要确认它们能否放进同一张表。

workspace、working directory 和 repo root 可能指向同一对象，也可能分别指容

器目录、进程工作目录和仓库根目录。归一化不能只靠字符串相似度，而要依赖术语表、实体映射或业务主数据。

薪酬场景中，E0007 和 0007 是否为同一员工，要查员工主数据；USD 100 和 SGD 100 不

能直接相加；按月统计与按结算周期统计也不能混在一起。

先统一身份和单位，后面的去重与冲突判断才有意义。

第三步：去重

不同 Worker 可能返回相同结论。聚合器需要区分两种情况：

  • 独立来源支持同一结论；
同一来源被多个 Worker 重复引用。

三张卡引用同一篇官方文档，可以说明多位 Worker 独立找到了同一资料，却不能直接当成三份相互独立的证据。

因此，去重至少要同时看：

  • 结论是否重复；来源是否重复；来源之间是否存在上游依赖。

两篇文章来自不同网站，也可能都在转述同一份公告。文本不同，不代表证据独立。可以通过向量相似度辅助发现近似表述，但是否源于同一个主文档，还要其它证据支持，进行进一步的分析。

第四步：处理冲突

聚合器发现不同值以后，不应立刻投票。它需要先判断冲突属于哪一种。

本讲中的两张卡属于“不同维度限定”，不是需要消灭的冲突。

只有在下面几项同时成立时，才应该采用投票策略：

  • 回答同一个命题；讨论同一个对象和版本；采用同一种取值语义；各路判断具有足够独立性；投票规则与业务风险相匹配。

第五步：检查接缝

单项结果全部通过以后，还要检查它们合在一起是否产生新的问题。

每个部门的付款都没有超过部门预算，所有部门相加仍可能越过公司资金线；每个微服务都满足局部延迟目标，完整调用链仍可能超出端到端 SLA；每份合同单独没有高风险条款，多份合同组合后却可能形成集中度风险。

第 32 讲的组合验收中，我们首先检查了责任覆盖；本讲则进一步检查跨分片不变量：

  • 总额是否越界？同一对象是否重复出现？不同工件是否引用了互不兼容的版本？局部结论组合后是否产生新的业务风险？

接缝问题通常不属于任何一个 Worker。它只能在聚合层被发现。

关键代码：报告要把分歧留下来 ​

python
当前实验中的 gather() 不直接返回一段自然语言总结，而是返回类型化报告：
@dataclass(frozen=True)
class GatherReport:
   """A typed result that keeps coverage, conflicts, and attribution."""
   verdict: Literal["isolated", "qualified", "insufficient"]
   accepted: bool
   missing_dimensions: tuple[Dimension, ...]
   conflicting_dimensions: tuple[Dimension, ...]
   cards: tuple[EvidenceCard, ...]

这几个字段承担不同职责。

cards 保留原始证据卡和来源，使聚合结论可以回溯。
missing_dimensions 说明哪些要求的证据尚未返回。
conflicting_dimensions 说明哪些维度内部仍有未解决冲突。
accepted 表示这份聚合报告是否满足结构准入要求。
verdict 表示当前证据支持哪一种业务表述。

这里必须分清两个概念：accepted 表示这份证据报告结构完整、内部没有未处理冲突，可

“材料齐全”与“结论为真”是两种不同判断。将二者放进同一个 success 字段，会让上层 Agent

很难区分到底通过了什么。因此，状态与结论分开，是更为严谨的做法。

2026 年的主流 Harness 如何实现扇出聚合模式 ​

现代 Harness 已经能够较方便地启动并行 Agent，但它们主要解决运行问题，而不是证据语义。

Anthropic 多 Agent 研究系统

Anthropic 的研究系统由 Lead Agent 创建多个 Subagent，让它们并行探索不同方向，再把压缩结果送回主上下文。这样的结构适合 breadth-first 查询：问题需要同时搜索多个来源和方向，单一上下文容易被检索过程占满。

Lead Agent 仍要负责分配范围、判断结果是否重叠、识别缺口并形成最终答案。Subagent 数量扩大的是搜索容量，不能替代聚合规则。

OpenAI Agents SDK

OpenAI Agents SDK 的编排指南展示了使用 asyncio.gather 并行运行多个 Agent 的方
式，output_type 可以为每路结果指定结构。运行时它可以帮助我们同时发起调用、等待多

路返回、收集成功与异常还有获得结构化输出。

它不会自动知道哪些分片应该到齐，哪些来源属于同一血缘，两个不同结论是真冲突还是维度

不同。这些规则仍然属于业务聚合器。asyncio.gather 能把结果放进同一个列表，但不能

替业务定义这个列表怎样变成可信结论，这些业务规则就是我们需要具体实现的部分。

DeepSeek Harness

本讲使用的 DeepSeek Harness 版本通过 ctx.subagents 提供统一子 Agent 接缝，可以挂
接 spawn、fork、ACP、Codex、Claude Code 与 dsh SDK 等 provider。

对于扇出聚合，这意味着不同 Worker 可以采用不同执行方式，而上层继续要求它们返回同一

种 EvidenceCard。生产实现可以由父编排器并发启动，或者启用后台运行，再把返回工件

送入确定性聚合器：

provider 决定任务怎样执行；
EvidenceCard 规定局部结果怎样表达；
GatherReport 规定多路结果怎样收回。

此时，Harness 管并发、会话与生命周期，而业务代码则负责覆盖、口径、冲突、溯源和接缝约束。

这些主流 Harness 的扇出聚合模式实现示例和细节，你可以参考佳哥的 Repo 中的 Readme说明。想提醒你关注的是，Harness 框架负责运行时实现，我们负责补全业务语义这个基本思路适合所有模式实现。

上线之后的观测指标 ​

生产系统中，可以对扇出聚合过程中的相关指标进行选择性的监控。

  • 分片覆盖率：预期分片中有多少返回了合格工件，缺失分片是否都被披露？

  • 独立证据率：去除同源重复后，真正独立的来源还剩多少？

  • 冲突保留率：已知冲突有多少被保留并送入裁决，多少被错误扁平化？

  • 增量收益：新增一个 Worker 后，带来的新覆盖或独立证据，是否抵得上额外的调用与聚合成本？

四项指标中，独立证据率最容易被高估。三位 Worker 返回三张卡不代表三份证据。聚合器应如实记录去掉同源转述后的来源数量。超时、拒收率和收口耗时则作为运行指标持续观察。

聚合器本身也需要版本和回归测试。词表变化、身份映射错误或冲突规则更新，都可能改变最终结论。因此，Worker 和聚合器都应该被监控。

什么时候适合使用扇出聚合模式 ​

扇出聚合适合输入能够天然分片的任务，例如按合同、客户、地区、代码目录或时间窗口拆分处理。它也适合需要多源核验的调查。同一结论需要官方文档、代码实现、运行配置和第三方资料共同支撑时，多路证据可以在相对独立的上下文中并行形成。

当业务窗口很短、等待成本高于调用成本时，并行也有直接价值。例如事故排查、风险扫描和临时决策支持，墙钟时间能比 token 成本更重要。

不过，这些任务仍需满足一个条件：每一路输出能够压成结构化工件，聚合规则能够说清楚。

下面几类情况不适合直接扇出：

  • 后一项必须读取前一项的完整中间过程；

  • 多位 Worker 需要同时修改同一份状态，却没有隔离工作区和合并机制；

  • 各路结果没有共同对象、单位和时间口径；

  • 最终只能把几段长文本交给一个更大的模型“凭感觉总结”；

  • 单 Agent 基线已经足够快，并行成本无法换来业务收益。

Worker 数量也不是越多越好。分片过细以后，调度、超时、重试、去重和聚合的固定成本会迅速增加。聚合器最终仍要消费所有局部工件，它可能成为新的上下文瓶颈。

规模较大时，可以采用分层聚合：

局部 Worker
 ↓
  • 分组聚合器
 ↓
  • 区域或主题报告
 ↓
  • 上层综合

此时每一层都需要保留覆盖、冲突和来源，不应该在中间层过早抹平。

总结一下 ​

扇出解决的是多路工作怎样同时推进，聚合解决的是这些结果怎样被收成一份不掩盖证据状态的报告。

真正的聚合不是把几段文字拼在一起，也不是看哪一边票数更多。它先检查分片是否到齐，再统一对象、时间和单位，随后识别同源重复，区分不同类型的冲突，最后检查局部结果组合以后是否违反全局约束。

这一讲的实验里，三位研究员分别回答会话、工作区和工具边界。扁平化投票把三种维度压成

一个布尔值，得到“完全隔离”的错误标题；类型化聚合保留 session=isolated、
workspace=shared 和 tools=restricted，最终形成 qualified 结论，并把共享工作

区风险一并交给下游。

这一讲最值得记住的是：能够并行返回的结果，不一定能够直接比较。好的聚合器不是尽快消灭差异，而是先判断哪些差异可以合并，哪些差异必须保留。

思考题 ​

  1. 你的多路结果真的在回答同一个字段，还是只因为都使用了“风险”“通过”“隔离”这些相似词，就被放进了同一轮投票？

  2. 聚合报告能否明确列出预期分片、已返回分片、缺席分片、未决冲突和每条结论的来源？
