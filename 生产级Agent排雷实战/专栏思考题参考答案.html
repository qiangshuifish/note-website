01｜Maker/Checker 如何防“共谋” ​

思考题原文：

  • 在宪法一中我们提到，为了防止模型“幻觉终止”，需要引入独立校验节点来判断目标是否真正达成。但如果执行 Agent 为了尽快完成任务，伪造了看似成功的“证据”（比如假装跑了测试、或者生成了假的成功日志）传给校验模型，导致校验模型也产生了误判。如何设计更健壮的 Maker/Checker 机制，来防范这种“执行模型欺骗校验模型”的共谋风险？

参考答案：

别让 Checker 读 Maker 写的成功日志，那等于让被告自己写判决书。Maker 只提交产物引用、commit hash、测试命令和参数；Checker 用独立身份在干净环境拉取固定版本，重新跑测试，并查询 CI、对象存储、工单和目标系统的真实状态，证据必须由这些外部系统签发。能用退出码、哈希、状态码判定的，就不要交给模型判断。只有语义质量这类没法机验的部分，才交给低温度、不同模型族的裁判按 rubric 打分，并随机化材料顺序、保留分歧。主观任务可以多评委，但仍然有误判概率，不能包装成零风险。

参考来源：

  • https://arxiv.org/html/2306.05685

  • https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works

  • https://claude.com/blog/building-effective-human-agent-teams

02｜多步写操作部分成功怎么办 ​

思考题原文：

本讲通过 ToolMeta 让 Loop 实现了并发控制和红绿灯重试。但假设模型在一次回复中连
续生成了两个有前后依赖的写操作（例如：先调用 freeze_account 冻结账户，再调用
send_email 发送冻结通知）。Loop 将它们串行执行时，第一步成功了，但第二步因网络
  • 问题连续重试失败最终报错。此时系统留下了“账户已冻结但未通知”的脏状态。在传统软件开发中，我们靠数据库事务（ACID）来保证要么全成功要么全失败；但在 Agent 架构中，工具调用往往是跨网络的独立 API，没有数据库事务可以依托。你能否在 Agent Loop 层面设计一种通用的机制，来解决这种“多步写操作的部分成功”问题？

参考答案：

这类跨服务写操作不要指望 ACID，应该提升为持久化 Workflow/Saga。每个动作在执行前登记幂等键、前后置条件、补偿动作和可逆性，失败后按 LIFO 逆序补偿，补偿本身也要幂等。

冻结账户和发送通知如果允许最终一致，更稳的是 Outbox：冻结事务同库写待发事件，后台Worker 至少一次投递，消费端去重。若要求同成同败，只有确认邮件没发出才能解冻；响应

未知时先查询投递状态或对账，不能盲目回滚。补偿再失败就进入 ROLLBACK_PENDING 挂

起人工。邮件、扣款这类不可逆动作尽量放在链路最后。

参考来源：

  • https://docs.temporal.io/guides/saga-pattern

  • https://docs.temporal.io/best-practices/error-handling

  • https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html?language=en_US

03｜超级客服如何动态切换角色且工具不超过 20 个 ​

思考题原文：

这节课我们通过 ToolRegistry 实现了 L1/L2/L3 三层架构，用角色隔离解决了工具混淆
  • 问题。但现实中有一种更麻烦的场景：同一个 Agent 在一次对话中，需要跨越多个角色边界——比如一个“超级客服 Agent”，在同一轮对话里既需要查客户 CRM 数据（crm 角色工具），又需要处理工单（cs 角色工具），还要偶尔查账单（billing 角色工具）。如果把所有角色的工具都加载进来，候选集就超过了 20 个上限；如果每次只加载一个角色，又无法在对话中灵活切换。你能设计一种机制，让超级 Agent 在对话过程中根据当前对话轮的意图，动态切换活跃角色，同时保证候选集始终不超过 20 个吗？提示：可以想想，这节课第三部分那套多维度评分的思路，能不能反过来用——不是从工具库里检索工具，而是从角色库里检索“该激活哪个角色”？

参考答案：

把角色当成工具目录的二级索引，而不是让模型在一大堆工具里硬选。每轮 PREPARE 根据当前意图、实体、动作和 Plan 下一步，对 CRM、客服、账单等角色卡打分，只激活一个主角色，必要时带一个只读副角色；常驻工具、主角色工具和少量副角色工具加起来硬截断到20。为了防抖，只有模型本轮确实调用了副角色写工具，下一轮才把它升成主角色，并加冷却和意图相似度阈值。跨角色写流程由编排器拆成串行子任务。20 不是协议规定，而是当前模型的注意力预算；工具继续增多时，应改成工具搜索和按需加载。

参考来源：

  • https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool?r=0

  • https://docs.anthropic.com/en/docs/build-with-claude/tool-use/implement-tool-use

04｜如何区分可安全降级和必须严格校验 ​

思考题原文：

本节课实现了字段的部分提取降级：当核心字段（如 order_status、tracking_id）
  • 提取成功而非核心字段失败时，系统接受部分结果继续运行。
但在某些业务场景下，“部分正确”比“全部失败”更危险。比如：订单状态从 pending 错更
改为 shipped，但物流单号为 null——这会导致下游物流系统订单号缺失，比直接拒绝
  • 更难排查。你能否设计一种机制，让 Agent Loop 能够区分“可安全降级的场景”和“必须严格校验的场景”？例如：通过在 Schema 上添加元数据标记，或者在 Loop 层维护一个“严格模式白名单”。

参考答案：

部分提取只能用于错了也容易纠正的低风险字段，状态、金额、权限、PII 和外部写入默认都

要严格校验。Schema 上直接标 critical、reversible、字段组和跨字段不变量；例如
status=shipped 时，tracking_id 必须非空且格式合法，否则整单拒绝、重试或转人
工，不能用 model_construct 把半成品塞进去。摘要、推荐、非关键标签可以允许

partial。这里要清楚，strict schema 或约束解码只能保证 JSON 形状和类型合法，不能证明值符合业务；订单状态机和服务端授权仍然要再验一次。

15｜如何区分真实推进和表演式忙碌 ​

思考题原文：

  • 我们用“单次任务预算熔断”解决了死循环烧钱的问题，又用“动态预算”尝试区分合法长任务和非法死循环。但动态预算的进度评估本身有个难题：怎么判断 Agent 是“真的在推进”还是“假装在推进”？假设 Agent 为了骗取追加预算，每轮都调用一个“看起来有进展”的工具（比如反复搜索不同关键词），但实际上没有获取任何新信息。它的动作指纹在变，工具调用在增加，可任务实质没有推进。请你设计一个“进度真实性评估器”，能区分“真实推进”和“表演式忙碌”。给你一个提示：单独看每轮调用都是无辜的，但把一串调用的信息增益放在一起看，会留下痕迹——真正的推进会带来新的状态变化、新的知识获取，而表演式忙碌只是在重复已知信息的不同排列。

参考答案：

数工具调用次数或比对动作指纹都容易被骗，模型每轮换关键词就能制造忙碌假象。进度评估要围绕目标状态：每个里程碑先定义可验证退出条件，工具结果统一归一成新实体、新字段、证据 ID/URL、内容哈希、代码 diff、测试结果、工单状态和外部系统状态变化，再做确定性去重，语义相似度只作辅助。连续 K 轮没有新证据、没有状态迁移、Plan 剩余路径也不变，即使调用数在涨，也判定为零信息增益，拒绝追加预算。合法等待外部事件必须声明等待对象、超时和退避策略；关键里程碑仍由独立探针或 Checker 验收。

参考来源：

  • https://claude.com/blog/building-effective-human-agent-teams

  • https://www.anthropic.com/research/trustworthy-agents?hl=en-US

16｜Prompt 升级后黄金轨迹大面积偏离怎么办 ​

思考题原文：

  • 漂移检测的前提是拥有一批人工标注的黄金轨迹。但当 Prompt 从 v2.1 升级到 v2.2、改变了退款策略判定逻辑时，新 Trace 必然与旧黄金轨迹大面积偏离，Evaluator 会误报并阻断灰度发布。你该如何设计黄金轨迹的版本化隔离或自动迭代更新机制？在人工标注成本高和自动学习可能引入脏数据之间，如何设计一个半自动的更新管线？提示：可以从 Dataset 版本管理、Prompt 版本与 Dataset 的关联、人工审核 + 自动候选的标注流程这几个角度思考。

参考答案：

只给数据集加内容哈希还不够，Prompt、Dataset、Evaluator 必须绑成版本三元组，否则分数没有可比性。发布 v2.2 时冻结对应数据集：v2.1 对旧集做回归，v2.2 的新 Trace 只对新集评估；策略变化先产出 policy diff，圈出受影响用例。生产 Trace 可以经聚类、去重后生成候选gold，LLM 也能写差异说明，但成功 Trace 不等于正确 Trace，必须人工审核后才能进入新数据集。未审核候选只作参考，不参与灰度阻断；核心安全用例不能自动修改，旧数据集保留用于回滚和审计。

参考来源：

  • https://docs.langchain.com/langsmith/manage-prompts

  • https://docs.langchain.com/langsmith/manage-datasets

  • https://docs.smith.langchain.com/tutorials/Developers/backtesting

17｜ChainOptimizer 冷启动期怎么运行 ​

思考题原文：

  • 反馈层靠生产数据挖反模式、写规则，但有个“冷启动”问题：系统刚上线时没有生产数据，规则库是空的，阈值只能拍脑袋；而拍脑袋的阈值可能导致大量误报或漏报，反过来影响生产数据的质量。问题：你怎么设计 ChainOptimizer 的冷启动策略，让系统在没足够生产数据时也能合理运行，随着数据积累再平滑过渡到数据驱动？提示：可以从“保守阈值加观察模式”起步、用合成数据预校准、人工审核队列做过渡期兜底这几个角度想。

参考答案：

冷启动不等于只能拍脑袋。DAG 无环、高危操作前审批、写操作幂等、补偿存在、关键路径上限、外部依赖数量限制这类结构性规则，第一天就可以硬拦，因为它们不依赖线上数据。需要学习的是启发式评分：先用专家模板、合成好 / 坏 Plan 和少量人工种子集预校准，上线初期只 WARN 不阻断，边界案例全部进人工队列。人工结论回流后，按业务域统计误报和漏报、调整阈值，稳定规则再逐步升级成 CRITICAL 门禁。合成数据只补稀有反例，不能代表线上分布；紧急场景始终保留人工通道。

参考来源：

  • https://developer.nvidia.com/blog/evaluating-and-enhancing-rag-pipeline-performance-using-synthetic-data

  • https://www.anthropic.com/research/trustworthy-agents?hl=en-US

18｜如何挡住不在黑名单里的隐性越权副作用 ​

思考题原文：

  • 最后留个问题，不用急着回答，带着它去看你自己的 Agent。“定义禁止而非允许”这套哲学很有力，但现实里，“禁止”清单本身很难枚举干净。还是拿退款举例：我们禁止 Agent 调delete_user_account，这条没问题。可万一它调的是 update_user_account 呢？表面看这个工具人畜无害，但它在退款过程里“顺手”把用户的 VIP 等级改成了普通会员。这当然也是违规，是一次越权的副作用，可它并不在你的禁止清单上，而你也不可能把所有会产生副作用的调用一个个列进黑名单。问题来了：能不能设计一种机制，不用枚举所有“禁止的副作用”，就能保证 Agent 每次工具调用的参数都落在预期范围内，把这种不显性的越权也挡在外面？

参考答案：

黑名单枚举不完，问题的关键是“白工具、黑参数”。最优先是按业务动作拆窄工具：退款上下

文只给 process_refund，修改会员等级另做工具、另走授权。确实需要宽工具时，按 Plan

步骤签发 per-tool、per-resource、per-field scope 和字段掩码，未声明字段直接拒绝，而不是悄悄剥离。strict schema 负责类型、枚举和值域，服务端策略再检查订单状态、操作者身份以及允许的状态 delta；高危写入前可以先 dry-run diff，执行后比对真实状态变化。测试也要断言本次调用只允许产生哪些副作用。

  • https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization

19｜如何自动识别可能过期的 gold 用例 ​

思考题原文：

  • 最后留个问题，带着它去看看你自己的 Dataset。数据层我们设计了 review_status 和 confidence，要求生产 Trace 入库必须人工审核才能升gold。但现实里，Agent 的行为是动态演进的：今天审核通过的 gold 用例，三个月后业务规则一变，它可能反而成了“错误答案”。想象你维护着一个 500 条用例的 Dataset，每条都定期人工复审，成本高到扛不住；可要是不复审，过期的 gold 会在回归检测里把正确的新行为误判成退化。你能不能设计一种“用例健康度”机制，自动识别哪些 gold 可能已经过期、主动提醒复审？换句话说，在“全量人工复审太贵”和“过期用例污染评估”之间，怎么搭一条可持续的Dataset 维护流程？

参考答案：

全量定期复审扛不住，但让系统按模型新输出自动改 gold 更危险，会把评估集改造成迎合模型的样子。更合适的是给每条 gold 建健康度：记录业务域、owner、最后审核时间，以及依赖的政策、Prompt、工具 schema 版本、历史失败率和生产分布偏差。依赖版本变更、线上Trace 与 gold 成簇偏离、Judge 分歧升高、工具字段失效、输入分布漂移或长期未审时，就降低健康分并送入复审队列。系统只标记“可能过期”，由人判断是模型退化、gold 过期还是有

意策略变更；确认后再创建新版本并用 replaces 指向旧用例，核心安全用例不自动隔离。

参考来源：

  • https://docs.langchain.com/langsmith/manage-datasets

  • https://docs.langchain.com/langsmith/run-backtests-new-agent

  • https://www.promptfoo.dev/docs/configuration/test-cases/

20｜矛盾 Skill 漏检后，运行时如何确定性仲裁 ​

思考题原文：

  • 我们用矛盾检测解决了 Skill 自相矛盾的问题，但矛盾检测本身依赖 LLM 的判断，它可能漏掉冲突，也可能误判两个不冲突的指令为冲突。假设 LLM 在 patch 时漏掉了一个真实冲突，两条矛盾的指令同时存在于 Skill 中。Agent 执行时，它会随机选一条执行，导致行为不稳定，有时候查 Sentinel，有时候查 Cluster，完全不可预测。在无法保证 LLM 矛盾检测 100% 准确的前提下，设计一种“运行时冲突仲裁”机制，让Agent 在遇到矛盾 Skill 时不会随机选择，而是有一个确定性的仲裁策略。提示：结构化Skill 的前置条件和版本号可以作为仲裁依据——新版本的条件分支应该覆盖旧版本的无条件指令，但怎么让 Agent 在运行时“知道”哪个是新版本、哪个该优先？

参考答案：

运行时不能把两条矛盾指令都塞给模型，让它凭概率挑一个。每个 Skill 应带 skill_id、语
义化版本、前置条件、动作效果、supersedes、签名和验证状态，由确定性的
SkillResolver 选择唯一胜者。硬安全约束最先；然后看哪条规则的前置条件与当前观测

事实匹配且更具体；同一 Skill 谱系内，再按 semver 和显式 supersede 关系选择已通过影子验证的新版本。跨 Skill 无法判断先后、证据不足，或条件同时命中但动作冲突时，应 fail-closed，只做只读补观测、向用户澄清或转人工，并写 Trace 生成冲突工单。版本号不能脱离谱系和验证状态单独决定胜负。
