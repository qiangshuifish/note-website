# 23 | 自我改进：让Harness越用越聪明

你好，我是徐昊，欢迎继续学习驾驭工程。今天我们要讲的主题是 Harness 的持续改进。

可能你会觉得：既然模型一直在升级，那么我们只要等待更强的模型，Harness 就自动跟着变好了。然而除了等待模型升级之外，我们更应该关注的是对技能（Skill）的改进。

这是因为在构造 Harness 的过程中，我们会积攒大量的技能，也正如前面课程里讲到的，技能是 Harness 内层循环实现的主要载体。除了自建技能之外，我也会通过引入大量的第三方技能，完善 Agent 的能力。

等模型升级，是花钱等更强的模型，而改进技能，是花力气让现有模型发挥得更多。前者不由我们控制，后者完全掌握在我们手里。

## 持续改进要做的四件事儿

虽然技能是 Harness 的主体，但它不是攒得越多越好。真正的成功，靠的不是积累更多技能，真正决定成败的，是四件事：生命周期管理、验证、抽象、维护。

- 生命周期管理，是说一条技能有它自己的生老病死。它从一次失败里诞生，被反复使用，可能逐渐过时，最后该退役。攒下它只是开始，之后每一步都要有人管，什么时候该改、什么时候该留、什么时候该扔。

- 验证是指一条技能不能写出来就采信。它得被检查，触发的时候对不对，产出的时候好不好，用了这么久有没有帮上忙。

- 抽象是说技能要提炼成可复用的步骤，而不是把某一次的具体经验原样存下来。存下来的是“怎么做这一类事”，不是“那次是怎么做的”。抽象得越好，它越能跨任务复用。

- 维护是说技能不是写完就结束了。它引用的接口会变，它服务的场景会变，模型也在变。技能得跟着改，不然就会从帮手变成坑。

所以持续改进不是持续往 Harness 里加技能，而是持续做这四件事，让技能成为被管理的资产。

这四件事里，最核心的是验证。另外三件都要靠它：生命周期管理要判断什么时候该改、该扔，得先知道这条技能行不行；抽象要确认提炼出来的步骤对不对，得靠检查；维护要发现接口变了、场景变了，也得靠检查。验证落到具体的做法上，就是给技能配备相应的评估机制（eval）。

## 如何评估一个技能

评估一个技能，主要就是回答三个问题：它的触发是否有效、执行结果如何、长期看它的效率如何。三个问题对应三类信号。

- 第一类，触发精度。该触发的时候触发没，不该触发的时候触发没。前者叫漏，后者叫误。很多技能的死因不是内容写得不好，而是触发器（description）写得不好，导致该触发时不触发、不该触发时乱触发。一个根本不触发的技能，内容写得再好也等于不存在。

- 第二类，输出质量。触发了之后，结果对不对、步骤对不对、风格对不对。这实际考察的是前馈与反馈的质量。

- 第三类，效率。延迟、token、成本。效率和质量必须成对看。一个技能为了保险，每次都把整个代码库读一遍才开始干活，token 比必要的多花好几倍，输出质量却和“只读相关文件”一样。单独看它的做法很稳妥，其实是更贵还没让质量变得更好。反过来，如果把技能优化到只读必要文件，token 降了一半，便宜了但质量也掉了，得不偿失。

有了这三类信号，我们就能综合评价一个技能的实际效果了。而评估的流程分为四步。

1. 写用例。给这条技能写一组 prompt，每条配一个“什么叫做好”的标准。起步 10 到 20 条，外加至少一条负面控制：一个“不该触发这条技能”的相邻请求，专门抓误触发。

2. 跑。让 Agent 带着这条技能，把这些用例一条条跑一遍。

3. 检查打分。对照标准检查每条结果，得出一个分数。检查分两层：一层是确定性检查，跑没跑、文件生没生，客观但覆盖面窄；另一层是评分标准（rubric）评分，看风格、完整性、步骤对不对，灵活但能被刷新。两层一起用，彼此补足对方的短处。

4. 对比。这个分数有两个用途：和上一次的分数比，看这条技能有没有退步；和没带技能的分数比，看这条技能到底带来多少提升。后者尤其重要，因为它测的是“净提升”，不是“写得规范”。结构写得再漂亮，只要没带来行为上的提升也没用。

### 一个例子

现在让我们以写周报的技能为例，看一下怎么完成这个评估流程。

首先是写测试用例，我们需要根据内容和触发情况的要求，来设计测试用例，比如：

- 帮我写本周周报，这周上线了反馈功能、修了三个

- 内容·亮点数量有至少两个亮bug、做了两次代码评审

C2

- 内容·亮点数据每个亮点都带30%，响应时间从 800ms 降到 300ms

这张表里，用例分成了两族：C 开头的是内容用例，T 开头的是触发用例。两族合起来，覆盖了三类信号里的两类。

内容用例的四条，输入各不相同，每条都按它要考的那个点来设计。

- C1 给的是一周里干了好几件事，看技能能不能提炼出至少两个亮点；

- C2 给的是带数字的结果，看技能会不会把数据带进亮点；

- C3 给的是一个被卡住的联调，看技能会不会把阻塞项写清楚、写对责任人和原因；

- C4 给的是一周里杂七杂八的事项，看技能能不能收进四段结构、写得客观不套话。

为什么要配四条不同的输入？因为“什么叫做好”不是一个整体，而是拆开的。一份周报好不好，至少有四个可以单独判断的维度：亮点够不够、亮点带不带数据、阻塞项有没有写明责任人和原因、整体是不是按四段结构来、有没有套话。

如果只写一条“把周报写好”，跑完之后只知道“好”或“不好”，却说不出哪里好、哪里不好。拆成四条，每一条只盯一个具体问题，这条技能到底是“亮点会写、但阻塞项写不清”，还是“结构都对、但全是套话”，一眼就能看出来。

接下来，我们需要使用提示词，逐条触发技能，并实际评估触发的结果。触发的方式有很多种，可以通过一段代码触发，比如后面这样：

```python
#!/usr/bin/env python3
import json
import re
import subprocess
import time
from pathlib import Path
HERMES = "hermes"
SKILL_NAME = "weekly-report"                      # 被测技能名（SKILL.md 里的 name）
LOAD_MARKERS = ["skill_view", "skill_load"]       # 加载技能的工具名，按版本调
# 用例：id / prompt / 预期是否触发
CASES = [
   {"id": "C1", "prompt": "帮我写本周周报，这周上线了反馈功能、修了三个 bug、做了两次代码评
   {"id": "C2", "prompt": "帮我写本周周报，反馈功能上线后点击率提升了 30%，响应时间从 800
   {"id": "C3", "prompt": "帮我写本周周报，支付联调被第三方接口文档卡住了，小王在负责跟进"
   {"id": "C4", "prompt": "帮我写本周周报，这周比较杂：上线了反馈功能、修了三个 bug、开了两
   {"id": "T1", "prompt": "帮我整理一下这周做了什么", "expect_trigger": True},
   {"id": "T2", "prompt": "帮我写一封给客户的道歉邮件", "expect_trigger": False},
   {"id": "T3", "prompt": "帮我总结一下这封邮件", "expect_trigger": False},
]
def run_one(prompt: str) -> dict:
   """用全新 hermes 进程跑一条 prompt。每个进程都是全新会话 = 干净上下文。"""
   t0 = time.time()
   proc = subprocess.run(
       [HERMES, "chat", "-q", prompt],           # -q 单次执行，非交互
       capture_output=True, text=True, timeout=600,
   )
   return {
       "elapsed_s": round(time.time() - t0, 2),
       "stdout": proc.stdout or "",
       "stderr": proc.stderr or "",
   }
def skill_triggered(raw: str) -> bool:
   """触发判定：工具调用日志里出现「加载被测技能」的动作。"""
   for marker in LOAD_MARKERS:
       if marker in raw and SKILL_NAME in raw:
           return True
   return False
def extract_tool_calls(raw: str) -> list[str]:
   """粗抽工具调用行。正式版应解析 sessions 导出的 JSONL，拿完整结构化 trace。"""
   pattern = re.compile(
       r"^\s*(read_file|write_file|patch|search_files|terminal|execute_code|"
       r"web_search|web_extract|skill_view|skills_list)\b", re.M)
   return [ln.strip() for ln in raw.splitlines() if pattern.search(ln)]
def main():
   results = []
   for case in CASES:
       r = run_one(case["prompt"])
       raw = r["stdout"] + "\n" + r["stderr"]
       triggered = skill_triggered(raw)
       ok = triggered == case["expect_trigger"]
       results.append({
           "id": case["id"],
           "prompt": case["prompt"],
           "expect_trigger": case["expect_trigger"],
           "triggered": triggered,
           "pass": ok,
           "elapsed_s": r["elapsed_s"],
           "tool_calls": extract_tool_calls(raw),
           "output_tail": r["stdout"].strip()[-2000:],   # 最终输出（skill 的产出）
       })
       verdict = "✓" if ok else "✗"
       print(f"{case['id']}  触发={'是' if triggered else '否'}"
             f"（预期{'是' if case['expect_trigger'] else '否'}）{verdict}"
             f"  耗时 {r['elapsed_s']}s")
   Path("eval_results.json").write_text(
       json.dumps(results, ensure_ascii=False, indent=2), encoding="utf-8"
   )
   print(f"\n已跑 {len(results)} 条，结果写入 eval_results.json")
if __name__ == "__main__":
   main()
```

当然正如我们之前讲过的一样，代码本身不重要，我们只需要理解这段代码的目的，就可以让大模型帮我们写出来。

最后是评分评估，在有了执行结果的基础上，可以交由大模型打分。比如后面这样。

- 你是技能输出的质检员。你的唯一任务是：对照给定的评分标准，判断下面这段内容是否达标。你只做这一件事

- 判断规则：

```
1. 评分标准是唯一依据。内容写得再流畅、再详细，只要不符合标准，就给 0。
2. 有疑问时判不通过。标准没明确要求的，不算加分项，也不拿它来放行。
3. 只有 0 和 1 两个分数，不存在「基本达标」的中间分。
```

- 输出格式（严格遵守，只输出两行）：

```
第一行：0 或 1
第二行：一句不超过 20 字的理由，直接指出哪里达标、哪里没达标
```

- 评分标准：

```
{rubric}
```

- 待评内容：

```
{output}
填上 C2 的例子：
```

- 评分标准：每个亮点都要带具体数据（数字、百分比或前后对比）

- 待评内容：

```
1. 上线了反馈功能，点击率提升了 30%
2. 修复了三个 bug
3. 开了一次需求评审会
```

- 裁判输出：

```
0
第 2、3 个亮点没有数据
```

- 三条规则各有针对：

```
第 1 条防「被学会宽松」——写周报的技能可能越演化越会说漂亮话，规则钉死「标准是唯一依据」，让裁判不
第 2 条防「有偏裁判」——有疑问时宁可判不通过，堵住「看着差不多就放行」的倾向。
第 3 条 + 输出格式，是为了让裁判的回答能直接被程序解析进结果表，而不是变成一段要人再读一遍的评语
```

这样，我们就完成了对于写周报技能的评估。

## 利用评估建立持续改进

前面说过，让技能成为被管理资产的是四件事：生命周期管理、验证、抽象、维护，而验证是核心，另外三件事儿都要靠它。

接下来我们就看看一套 eval 到底怎么支撑起另外三件事。

生命周期管理，管的是这条技能什么时候改、什么时候留、什么时候扔。这三个判断，每一个都得先知道“这条技能现在行不行”，而「行不行」的依据就是评估的结果。其中改和留比较直观，如果评估没有下降，就保留。而如果评估判断输出质量下降，或触发精度降低，那么进行相应的修改就可以了。

而是否应该废弃技能的判断稍微复杂一些。有两个信号。一个是把技能卸掉再跑一遍评估，还能全过，说明这些能力已经被模型内化了或是被其他技能取代了，技能没坏，只是没用了。另一个是持续失败，几个版本下来分数一路走低、怎么改都救不回来，就该废弃。

而抽象，是把技能提炼成可复用的步骤，这一步类似于重构。也就是在保持技能功能不变的情况下，用更精简的模式来书写它。因此要检查提炼出来的步骤对不对，不能 Agent 自己说了算，得靠检查。比如，写周报的技能，转换为模板替换的写法可能更通用，也更精简。但是还要保证对应的测试能够通过评估。比如 C4 验结构对不对、有没有套话，C2 验数据有没有真的进到亮点里。

维护，是应对接口变了、场景变了、模型变了。但变了没有，得靠检查来发现。接口变了，确定性检查里跑测试的那一步会失败；模型升级了，重跑一遍评估，行为变了就暴露。没有评估，维护只能在出事后才补救。

所以一套评估体系不只是给单个技能打分，它是把生命周期管理、抽象、维护从凭感觉变成看信号。每一次判断，都有一个分数可依。落到日常操作，就是把它反复跑起来，主要在两个时机。

第一个时机，每次改完这条技能之后。改之前跑一遍，存一个分数；改之后跑一遍，再存一个分数。两个分数一对比，就知道这次改动是让它变好了还是变坏了。这就是前面“对比”那一步的落地：和上一次比，看有没有退步。比如给周报技能改了一段指令，想让阻塞项写得更清楚，改完一跑，发现“亮点数量”那条用例反而没过。不用猜，diff 摆在面前，这次改动带来了回归。

第二个时机，每次模型或运行时升级之后。上个月还好好的一条技能，模型一换，行为可能就变了。周报技能在旧模型上老老实实按四段写，换了新模型，可能开始自由发挥。所以模型升级不是坐等变好，而是一个要重新跑评估的信号。

把这些拼到一起，一条 skill 的持续改进方案就成型了：每次动它，改前改后各跑一遍，diff 看有没有退步；每次模型或运行时升级，把整条 eval 重跑一遍，看行为有没有走样。前一条线管“自己有没有改错”，后一条线管“环境有没有把它带偏”，两条线合起来，正好覆盖一条 skill在生命周期里最主要的两种风险。这样一来，改、留、扔的判断、抽象的对错、维护的变化，每一个动作背后都有一个分数可依。持续改进不再是一句口号，而是一套固定的节奏。

## 小结

- 技能的持续改进不是攒更多技能，而是做好四件事：生命周期管理、验证、抽象、维护。这四件里验证是核心，另外三件都要靠它。

- 验证落到做法上，是给每个技能配一套 eval，测三类信号：触发精度（该触发的漏没漏、不该触发的误没误）、输出质量、效率。效率必须和质量成对看。

- 评估四步：写用例（10 到 20 条加一条负面控制）、跑、检查打分（确定性检查 + rubric 评分两层互补）、对比（和上次比看退步，和没带技能比看净提升）。

- eval 支撑另外三件事：生命周期管理的改、留、扔靠分数定，抽象的重构靠检查确认步骤没走样，维护靠重跑发现接口、场景、模型的变化。

- 持续改进落成固定节奏：每次改完跑一遍看回归，每次模型升级跑一遍看走样，改、留、扔和抽象、维护的每一个判断背后都有分数可依。
