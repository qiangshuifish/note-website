27 | AgentFirstWorkspace：使用外部Harness的基准模式 ​

你好，我是徐昊，欢迎继续学习驾驭工程。

今天我们要讲的是 Agent 优先工作区（Agent First Workspace）。Agent 优先工作区是我在今年（2026 年）设计的一种使用 Harness 的基准模式。现在几乎已经成为我构建不同 Harness的起点了。

这个模式源于一个非常简单的思考实验：如果我们希望尽可能最大化 Agent 的自主性，减少人对于 Agent 工作流程的打断，完全将如何优化 Agent 的工作流作为首要考虑因素，那么我们要做什么？

首先要明确一点，我们这么考虑，并不是说想把人从整个流程中取消掉，而是强化我们去思考“人应该出现在工作流的哪个位置”，哪些是必须的，而哪些是可选的。我们要尽可能去掉不必要的人为干预，仅仅保留必须的“human in the loop”。

那么 Agent 的工作流需要哪些东西呢？以及如果缺失了又会怎样呢？这个问题并不难回答，我们前面各种坏味道的章节中，其实陆续讲到了一些。

  1. 知道要做什么，也就是目标、规格和验收标准。如果出现缺失，那么 Agent 就会猜错方向，人要中途纠偏；

  2. 知道“这里是怎么做事的”，比如约定、环境、工具、风格。如果缺失 Agent 就会停下来询问；

  3. 知道当前状态，做到哪了、什么已完成、什么在等。如果缺失就会产生大量返工；

  4. 知道什么时候停，也就是完成的定义是什么。如果缺失，要么没做完就停，要么做完还不停。

人打断 Agent，几乎总是发生在这几样缺失的时候。所以“Agent 优先工作区”的第一原则就出来了：把一切本来要在“运行时”人回答的东西，提前写成工作区里的工件，让 Agent 去读取，而不是去问。

这等于把人的角色从“任务执行过程中的应答者”改成“任务开始前的规格作者”。人没有消失，只是从循环里挪到了循环外，这就是最大化自主性的本质：不是去掉人的判断，而是把人的判断前置、固化、可复用。

构建知识库 ​

得到这个结论并不困难，但这对于实际应用几乎没有帮助。这是因为受限于我们自身的认知能力，有很多东西我们也很难一开始就提供给 Agent。比如，当我们利用 Agent 写代码时，我们也很难了解代码的方方面面，永远会有遗漏，永远会有盲区。

因此我们首先要解决的问题，不是怎么把人知道的多写一点，而是人不知道的那些，怎么让Agent 还能拿到，方法就是构造 Agent 知识库。

Agent 知识库装的不是人知道的东西，而是让知识变得可获得的机制。它的写作者从来就不止一个人。拆开有四个来源。

来源一，人写的：地图、约定、意图。这一层是人亲手写进工作区的，但它写的不是知识，而是导航。

人的价值从来不在于把代码复述一遍，而在于告诉 Agent 三件事：入口在哪里，这个工作区分成几块，以及这里是怎么做事的。换句话说，人写的是“到哪里去读”，而不是“读到的内容”。一份好的地图应该短到 Agent 一眼能看完，又准到让它能据此找到任何东西——哪类信息放在哪个目录、什么约定适用于什么场景、出了问题先去哪看。

人在这里最容易犯的错，是误以为自己在写知识，结果写成了“复述”。复述会滞后、会腐烂，地图不会，因为地图指向的是活的源头，源头变了，地图仍然成立。

来源二，系统里本来就有的：代码、配置、git 历史。关于代码的最准确事实来源，就是代码本身。任何二手转述、任何文档里的描述，都不可能比代码更准确，文档会滞后，代码不会。配置文件和 git 历史也是同样的道理：环境怎么搭、依赖是什么、什么版本能用，去看配置比看任何人的口头描述都可靠；一个功能为什么长成今天这样、当初是为了解决什么而改的，git历史里躺着答案。

所以知识库在这一层要做的，不是复述这些原物，而是明确地告诉 Agent 直接去读原物，并且告诉它原物在哪里、按什么线索去读。这一层几乎不产生任何新文字，它只做一件事——把Agent 引向唯一可信的源头。

来源三，Agent 派生的：探索、索引、结构、摘要。前面两层，一层靠人写，一层靠原物，但中间还缺一道工序：把散落的原物组织成可以导航的结构。

这层工作人可以完全不做，交给 Agent 自己跑出来。Agent 可以读代码、建索引、抽出目录结构、写摘要——这些恰恰是人既写不完、也不该去写的东西，因为它们量太大，而且会随代码变化。让人去维护一份代码索引，等于让人去干机器更擅长的事，而且注定跟不上。

让 Agent 去派生，等于给知识库装了一台自动生成的引擎：代码一变，重跑一遍索引，出来的就是新的。这一层让“知识库必须靠人喂养”这个前提不复存在，知识库从此可以随系统自动生长。

来源四，Agent 沉淀的：决策、踩坑、纠正。前几层解决的是“读”，这一层解决的是“写回去”。Agent 在干活的过程中，会碰到不确定的地方、会做出判断、会踩到坑、会被人纠正——这些一旦发生，就应该就地写回知识库，成为下一次开工时的“已知”。

这么做的直接效果是：每一个问题只需要被解决一次。第一次遇到它是未知，第二次它就已经是知识库的一部分。一个踩过的坑、一条被纠正过的规则、一次艰难做出的决策，如果没有写回去，就会在下一次以同样的方式重演，而每一次重演都是一次不必要的人的介入。这一层是知识库真正“活”起来的来源：它不靠谁提前想到，而是靠使用过程本身把未知一点点变成已知。

举一个例子，比如我们现在使用 Agent 为代码库增加回归测试（regression test），那么我们的知识库可能是这样的。

人写的：地图、约定、意图

意图。回归测试的本质是防止修好的 bug 卷土重来，所以第一件只有人能提供的东西是，要预防哪个 bug。你必须在任务里写清楚——“上个月结算模块出过一个精度 bug，我要用测试锁死它不再复发”，或者“给支付核心路径整体补一张测试网”。这两种意图写出来的测试是完全不同的两套：前者是几条递进的测试，后者是一大片覆盖。这个意图，代码给不了，工具给不了，只有你能给。

约定。例子里就要约定“这里怎么做测试”。包括这个项目测试怎么组织：测试放 tests/ 还是和源码同目录、用 pytest 还是 jest、命名规则是 test_xxx 还是 xxx_test、怎么跑、要不要看覆盖率。

地图。指向现成的范例——“照着 tests/test_user.py 的样子写”。给 Agent 一个已经通过、风格正确的测试文件当锚点，比十条规则都管用。

系统里本来就有的：代码、配置、git 历史

代码本身。被测函数长什么样、有哪些分支、边界条件在哪、依赖什么外部资源——Agent 不读代码，写不出任何一条有价值的测试。

配置。依赖清单和测试运行配置告诉 Agent 环境长什么样：pytest.ini 里的设置、CI 工作流文件里测试是怎么被触发的、有没有数据库或外部服务。这些直接决定测试是能直接跑，还是必须 mock。

git 历史，这一层在这个任务里是主角。回归测试要防的“回归”，就存在 git 历史里：git log 告诉你最近修了哪些 bug、哪个文件改得最频繁、哪个模块反复出事；git blame 告诉你一段代码是谁、为了什么改的。这些正是回归测试最该锁住的地方。一个刚修过的 bug，就是最高价值的回归测试对象，而它只会在 git 历史里留痕，不在任何文档里。

Agent 派生的：探索、索引、结构、摘要

Agent 先跑一遍代码，抽出被测模块的公开接口和调用关系；再对比测试目录和源码目录，找出哪些函数至今没有测试覆盖——用现有覆盖率工具跑一遍，就能得到这张“缺口地图”。它还会读出哪些模块复杂、哪些是热路径、哪些带副作用（碰了网络、数据库、文件系统）——这些决定哪些测试要 mock、哪些能直接跑。这些不是人写的，是 Agent 自己跑出来的。

Agent 沉淀的：决策、踩坑、纠正

Agent 写的过程中会做判断、会踩坑。

  • 这个模块为什么用 mock 不起真数据库——因为 CI 里根本没有数据库服务；

  • 某个测试为什么在 CI 上时好时坏——因为它依赖了系统时间，换个时区就崩。这些判断和坑，当场写回知识库，下次加测试就不会再犯。

  • 人审完测试给的纠正，比如“这条没测到边界条件”“这个断言太弱，等于没断言”，同样写回去，成为下一次的标准。

合起来看，四种知识的角色一目了然，而且能看出它们不是四个孤立的盒子：Agent 沉淀的那批好测试，人挑几个认可了，就升级进“人写的”那一层，变成新的锚定范例，于是下一批测试就会写得更好。知识就在这四个来源之间转圈，越转越多。

回归测试这个任务尤其能说明问题——它最值钱的输入（最近修过什么 bug）不在任何人的脑子里，也不在任何文档里，只在 git 历史里；而它最终产出的财富（哪些坑、哪些范例）又会流回知识库，喂给下一轮。

定义工作流 ​

确定了知识来源，接下来的一步就是定义工作流了。这就是技能以及双层循环需要发挥作用的地方了。后续的章节里会让你看到更多的例子。这里暂时不做展开。

下发任务 ​

知识库建好了，工作流也定成了技能，接下来就是人真正能发挥作用的环节 + 下发任务。别的知识都可以前置、都可以交给机器，唯独“这次要做什么、为什么”，只能由人在这一刻给出。不过由于我们建立了知识库，也定义了工作流，下发任务也会变得简单起来。具体过程如下。

  • 给定一个任务说明，让 Agent 根据知识库和给定的流程，给出设计和方案；

  • 如果对于设计和方案不满意，调整任务说明，增加反馈和验收条件，直到满意为止；

  • 根据设计和方案，让 Agent 给出详细的 todo 和计划；

  • 在计划中增加人为检查点（当然，也可以完全交给 Agent 处理，不增加检查点）；

  • 让 Agent 开始工作。

小结 ​

  • Agent First Workspace 源于一个思考实验：最大化 Agent 的自主性，只保留必须的 humanin the loop。它的第一原则，是把一切本来在运行时由人回答的东西，前置成工作区里的工件，让 Agent 去读而不是去问。人不是被取消，而是从“执行中的应答者”变成“开始前的规格作者”。

  • 人打断 Agent，几乎总发生在工作流缺了这四样的时候：做什么、怎么做、当前状态、什么时候停。缺了它们，Agent 就会猜错方向、停下来问、反复返工，或在该停的时候停不下来。

  • Agent 知识库装的不是“人知道的东西”，而是“让知识变得可获得的机制”。它有四个来源：人写的（地图、约定、意图）、系统里本来就有的（代码、配置、git 历史）、Agent 派生的（探索、索引、结构）、Agent 沉淀的（决策、踩坑、纠正）。知识在这四个来源之间流转，越用越多。

  • 知识库解决“知识从哪来”，工作流解决“知识怎么被用起来”。技能把一类任务固化成可复用的过程，双层循环让它在使用中不断改进。这一讲你有个大概印象即可，后续章节还会展开。

  • 下发任务是两段式的：先下设计令——人给任务说明，Agent 出设计和方案，人审方向；再下执行令——人确认 todo，Agent 进 loop 执行。审设计是人的判断成本最低、价值最高的位置，检查点则是一个可以随时加撤的刻度。

今天我们仅仅介绍了 Agent First Workspace 的基本概念，可能有些抽象，不过没关系，后续我们会有几个例子，来演示如何通过 Agent First Workspace 完成复杂的工作，以及为什么它应该成为 Harness 的默认模式。
