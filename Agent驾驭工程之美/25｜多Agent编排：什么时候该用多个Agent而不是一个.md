# 25 | 多Agent编排：什么时候该用多个Agent而不是一个

你好，我是徐昊，欢迎继续学习驾驭工程。

今天我们要讲的主题是多 Agent 编排（Multi-Agent Orchestration）。

很多人把多 Agent 编排当成一种高级技巧，尤其爱拿它类比微服务，单体应用不行了就拆成微服务，一个 Agent 不够了就拆成多个 Agent。多 Agent 和微服务一样，都是在用“拆”换取“隔离”和“并行”。每个 Agent 有自己的上下文、自己的工具、自己的模型，就像每个微服务有自己的数据库、自己的部署、自己的技术栈。顺着这个类比，多 Agent 编排就成了 Agent 架构的最终答案，好像走到这里，架构就算毕业了。

但实际上，做技术非常怕这样盲目的类比，微服务拆分的关键是在围绕云平台弹性优先的前提下做独立部署。单纯把单体拆分成分布式单体，只能增加运行成本。这是当年微服务架构转型常犯的错误之一。而现在，对于多 Agent 的拆分，比微服务还要盲目。多 Agent 不是免费的，每多一个 Agent，就多一处可能失败的地方、多一套要维护的提示词、多一次交接时的信息丢失。

此外，多 Agent 并没有什么明显的好处。Anthropic 今年早些时候发布的文章里就提到过，他们见过团队花好几个月搭出一套精细的多 Agent 架构，最后发现把一个 Agent 的提示词改好一点，效果就一样了。另外，多 Agent 的词元（token）消耗通常是单 Agent 的 3 到 10 倍，需要额外的冗余上下文才能发挥作用。

依照我个人的经验，多 Agent 架构只适用于三类场景：第一个是，有严格的工作流，大模型只在工作流的节点上发挥作用，并不需要统筹全局；第二个是通过多 Agent 实现多路并发的情况；第三个是避免上下文污染，让 Agent 能够在不同的上下文窗口内独立思考。

## 一个典型的多 Agent 架构

以 TradingAgents 为例，我们看看一个多 Agent 架构是怎么落到具体任务上的。TradingAgents 是 Tauric Research 开源的 LLM 金融交易框架，它模拟的是一家真实的交易公司，分析师、研究员、交易员、风控、基金经理各司其职，协作输出一个买卖决策。它的多Agent 架构是一条四层流水线：

- 第一层是分析师团队，四个分析师同时开工，各管一摊。基本面分析师看财报和估值，情绪分析师抓新闻标题、StockTwits、Reddit 上的市场情绪，新闻分析师盯全球新闻和宏观指标，技术分析师用 MACD、RSI 这类指标找价格形态。四个分析师各自用自己的工具并行收集数据，全部报告交齐之后，才进入下一层。

- 第二层是研究员团队。这里的设计最特别：它拆成多头研究员和空头研究员两派，多头专门找看涨的理由，空头专门找看跌的风险，双方针对分析师团队的发现做结构化辩论。辩论的产出不是各说各话，而是一个平衡过的市场判断。

- 第三层是交易员。交易员综合分析师和研究员的所有报告，决定买还是卖、什么时机、多大仓位。

- 第四层是风险管理团队加基金经理。风控团队评估这笔交易的敞口、波动率、流动性，给基金经理出一份评估报告；基金经理批准或否决，批准了才把订单送进模拟交易所执行。

整条流水线里，绝大多数信息是结构化输出，一份份报告往下传，只有两处用自然语言对话，一处是研究员团队内部的多空辩论，一处是风控团队的讨论。

为什么这么设计？结构化输出能防幻觉、防信息丢失，而辩论必须靠对话才能碰撞出相反的观点。这种“该结构化就结构化、该对话才对话”的取舍，正是多 Agent 架构里最容易做错的地方。

那么这套架构的优势到底在哪？对照前面说的三个适用场景，TradingAgents 恰好把三个都占了。

- 第一个优势是并行，对应“多路并发”这一类。四个分析师查的是四类完全独立的数据源，财报、社交媒体、新闻、行情图彼此不干扰。让一个 Agent 顺序查这四样，慢，而且上下文会被塞满；拆成四个 Agent 并行，各查各的，最后汇总。这是多 Agent 最干净的一个用法。同时也是效率最高的做法

- 第二个优势是严格工作流，对应“固定流水线”这一类。分析、辩论、交易、风控、审批，这条路径是写死的，大模型只在每个节点上干它该干的活，不需要统筹全局。这和“让一个Agent 自由发挥”完全不同，它是把一家交易公司的组织流程直接搬进了提示词。

- 第三个优势是辩论。多头和空头两个研究员针对同一份数据给出相反观点，这种自我质疑是单 Agent 很难做到的。一个 Agent 写结论，往往会顺着自己的推理往下走，越写越自信；而让两个角色故意站在对立面，逼着互相挑毛病，能挖出单 Agent 忽略掉的风险。Tauric把这个叫“辩证推理”。

TradingAgents 不是一个为了多 Agent 而多 Agent 的炫技。它是先有一个真实存在的组织流程，也就是交易公司，再把这个流程映射成多个 Agent。这恰好是判断多 Agent 值不值的一个维度：如果你能说清楚每个 Agent 对应现实里的哪个角色、它们之间那条工作流长什么样，多Agent 就成立；如果说来说去只是“多几个 Agent 感觉更厉害”，那多半是又交了一笔嫉妒税（某某 -Envy）。

## 状态文件 + /loop 实现固定工作流

然而随着技术的进步，无论是严格工作流，还是多 Agent 并发，我们几乎不需要使用LangChain 之类的框架。正如前面文章介绍过的，我们可以使用流程锚定，来固化工作流。

```
如果担心固化效果，我们也可以使用状态文件，配合 /loop 实现固定工作流。
我们在前面的章节里，已经介绍了 /loop 的实现机制，这里就不再赘述了。那么如果使用
/loop 要怎么实现类似 Trading Agent 的架构呢？
```

TradingAgents 那条四层流水线，可以只用状态文件加几个 loop 拼出来。关键在于两处替换：把“Agent 之间的结构化消息”换成“状态目录里的文件”，把“流水线里谁先谁后”换成“文件之间的依赖”。

先把状态目录定好，每个角色的产出是一个文件：

```
state/
├── analysts/
│   ├── fundamentals.md
│   ├── sentiment.md
│   ├── news.md
│   └── technical.md
├── research.md
├── decision.md
└── approval.md
```

第一层四个分析师，是四个并行的 loop。每个 loop 的 prompt 只干一件事：读自己的数据源，把结论写进 state/analysts/ 里对应的文件。四个 loop 各写各的文件，互不干扰，这就是多路并发，只是并发的方式从“框架里并行派四个 Agent”变成了“四个独立 loop 各写各的文件”。而且每个 loop 都是独立上下文，谁的数据也不会塞进谁的窗口里，这又正好是第三个场景“避免上下文污染”。

第二层研究员团队，是一个 loop，触发条件是“四个分析师文件都写完了”。它的 prompt 是：读四个分析师报告，写出多头看涨和空头看跌两边的理由，把平衡后的结论写进research.md。注意这里辩论不再是两个 Agent 实时对话，而是一个 loop 在文件里同时写下两边的理由。

第三层交易员，是另一个 loop，触发条件是 research.md 写完了。读研究结论，把买卖决策写进 decision.md。

第四层风控加审批，是最后一个 loop，触发条件是 decision.md 写完了。读交易决策、评估风险，批准就写进 approval.md 并送模拟交易所，否决就退回让交易员 loop 再跑一轮。

这样，原来那条“分析师 → 研究员 → 交易员 → 风控”的流水线，就变成了“四个并行 loop →一个辩论 loop → 一个决策 loop → 一个审批 loop”，loop 之间不直接对话，全靠状态文件交接就可以了。

```
这里需要注意的是，对比 Trading Agent 的多 Agent 版本，状态和 /loop 的版本在触发效率
上，可能有所不如，毕竟是依靠 /loop 轮询的，触发时机没有自主编排的准确.
```

## Subagent 实现上下文分离以及并发

如果不涉及固定工作流，而只是希望能够分离上下文和并发，比如类似 TradingAgents 中辩论的场景，或是研究员同步调查的场景，那么我们可以通过 Subagent 的方式来实现。

Subagent 是主会话派生出来的独立 Agent，有自己的上下文窗口、自己的工具列表、自己的模型，干完活只把最终结果交回主会话，中间的过程主会话看不见。目前 Agent 框架使用Subagent 的方式，主要是在独立的 Subagent 中调用技能（skill）或者工具（tool）。比如，

```
Claude 就在技能的元数据中，增加了一个 context: fork，来表示这个 skill 会由一个
```

Subagent 来执行。

有了这套机制，我们就不需要额外编写多 Agent 协调器了，写两个 skill，让它分别在两个Subagent 去并行查不同的数据源，就已经是一个多 Agent 系统了，只是它藏在 skill 和Subagent 的组合里，没有单独的通信协议，也没有多 Agent 协调器。

## 小结

- 多 Agent 编排不是高级技巧，也不是架构的最终答案。它和微服务一样，用“拆”换“隔离”和“并行”，但每次拆分都有代价：多一处失败点、多一套提示词要维护、多一次交接的信息丢失。

- 多 Agent 只值得在三类场景里用：严格工作流、多路并发、上下文隔离。除此之外，把提示词改好往往比搭多 Agent 更划算，而多 Agent 的 token 消耗是单 Agent 的 3 到 10 倍。

- TradingAgents 展示了典型的多 Agent 架构：四层流水线里，分析师并行收集、多空研究员辩论、交易员决策、风控审批。它恰好落在三类场景里，其中“辩论”是单 Agent 很难做到的，这才是它最不可替代的地方。

- 严格工作流和多路并发，用状态文件加 /loop 就能实现，不需要多 Agent 框架：把 Agent之间的消息换成状态文件，把流水线的先后换成文件之间的依赖。

- 上下文隔离和并发，用 Subagent 就能实现：让 skill 以 Subagent 执行（context: fork），或者在 Subagent 里调用 skill，就已经是一个多 Agent 系统，不需要自己写协调器。
