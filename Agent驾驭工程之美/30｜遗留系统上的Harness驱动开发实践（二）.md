# 30 | 遗留系统上的Harness驱动开发实践（二）

你好，我是徐昊，欢迎继续学习驾驭工程。

上一讲我们讲解了如何为遗留系统构造知识库。今天我们接着讲解一下，如何在知识库的基础上利用 Agent First Workspace 完成我们要进行的操作。

先让我们从一个简单的任务开始——为遗留系统增加回归测试（regression test）。毕竟遗留系统之所以成为遗留系统，主要是知识和认知缺失，同时工程上往往伴随着测试缺失。为了在遗留系统上更好地工作，增补测试是开始的第一步。

## 为任务补充知识

上一讲中，我们围绕着服务提供的 API 和消费的 API 提取了知识。但是这些知识是否足够我们完成当前的任务呢？可能还是不够的。毕竟 spec 和 contract 记录的，是“接口长什么样”，这个服务提供了哪些 API、每个 API 的路径和方法、它又调用了别人的哪些 API，这是一份接口知识。

但回归测试要测的，恰恰不仅仅是接口本身，还有接口背后的行为，给一个确定的输入，系统应该返回什么、应该发生什么。

所以知识提取并不是一蹴而就的，哪怕我们一开始已经做了准备，但是遇到具体任务的时候，还是会出现知识缺失的情况。因为知识是为任务服务的，而任务还没发生的时候，没法预知它会用到哪一块知识。

上一讲我们说过，试图把业务背景一次性补全是徒劳的；同样的，试图把知识一次性提取干净，也是徒劳的。能提前做的，是搭好知识库的骨架。至于某个具体任务需要的那块知识，只有等任务来了，才能知道它缺在哪、该往哪补。

所以知识提取的正确姿势，不是提前囤够，而是任务驱动。拿到一个任务，先拿现有知识试一试，哪里不够、哪里读不懂、哪里下不了手，缺口就自然暴露出来；然后针对这个缺口，回到代码、回到业务注释里去补。补完这一块，知识库就长大了一点，下一个任务再补下一块。

回到回归测试这个任务，事情就很具体了：拿着上一讲的 spec 和 contract 开工，发现缺的是行为知识。这个“缺”不是失败，而是任务驱动的正常一步——它逼着我们问一个更准的问题：写回归测试，到底需要知道每个 API 的哪些行为。

那么，我们可以增加一个 skill 来弥补这个知识。比如下面这样：

```
name: implement-flow
description: 从每个 HTTP endpoint 出发，梳理它被调用后依次做了什么（调哪些下游 API、查哪些数
```

- 目标

```
对每个服务，从 api.spec.md 里的每个 endpoint 出发，读代码梳理调用链，写成 wiki/{repo}/end
```

- 步骤

```
1. 读 wiki/index.md 拿服务清单，读每个服务的 api.spec.md 拿 endpoint 列表。
2. 在 checkout/ 下定位每个 endpoint 的处理函数（controller / route handler）。
3. 顺着处理函数往下追，按顺序记录它做的事：
  - 调了哪些下游 HTTP API（标出目标服务和路径）
  - 查 / 写了哪些数据库（标出表或集合）
  - 发了 / 收了哪些消息队列
  - 关键分支：什么条件下走哪条路
4. 每个 endpoint 画一张 mermaid 调用链：
mermaid
flowchart TD
   EP[POST /orders] --> A[查询用户]
   A -->|用户不存在| ERR[返回 404]
   A -->|用户存在| B[调用 service-b: POST /inventory/lock]
   B --> C[写 orders 表]
   C --> D[发送 order.created 消息]
   D --> OK[返回 201]
5. 写成 wiki/{repo}/endpoint-flows.md，每个 endpoint 一节。
```

- 验证

```
读 wiki/index.md 和每个 api.spec.md，核对每个 endpoint 都有对应的 mermaid 图，缺任何一个
```

- 注意

```
- 只梳理"对外可见的行为"：调了什么、查了什么、发了什么、返回什么，不写内部实现细节。
- 追到服务边界为止：调下游 API 时标出目标服务和路径即可，不展开下游服务的内部。
- 分支要如实画：认不准的条件或走向，标"待确认"，不要猜一个填进去。
- 这一步产出的就是行为知识，正是回归测试要测的东西。画图的目的是让"这个 endpoint 被调用后到底做
```

通过这个 skill，我们把接口知识补成了行为知识，其中的 mermaid 流程图告诉我们每个endpoint 被调了之后具体走哪几步、查什么、调谁、什么条件分叉。这张图天然就是回归测试的提纲。图上的每一个分支、每一个下游调用、每一个落库点，都是一条该被测试覆盖的路径；图里标“待确认”的地方，恰恰是最该先补测试、最可能藏雷的地方。这样，Agent 就不用再凭空猜测“这个 endpoint 该测什么”，照着图一条条覆盖就行。

这里我们有另一个选择，就是让 LLM 直接去读源代码。如果代码规模不大，这的确也是一个可行选项，但是我并不建议这么做。因为在后续的操作中，我们需要根据实现的路径，设计测试案例以及实现测试代码。源代码会占据上下文，并分散大模型的注意力。而且每次重复理解同样的代码也是一种浪费。那倒不如就以 mermaid 流程图的形式，把代码的实现知识存入知识库中。

对于代码库，这是一种常用的上下文压缩技巧，我们可以几乎无损地保留代码实现的知识，同时大量减少上下文的空间。

## 构造回归测试的流程

在补充完知识之后，我们就可以开始着手设计回归测试的流程了。这个流程相当简单：设计回归测试案例 → 把回归测试案例实现为代码。

我们可以很容易地为这个流程的两个环节设计 skill，比如：

```
name: test-case-design
description: 根据 implement-flow 产出的 endpoint-flows.md，为每个 endpoint 设计回归测试
```

- 目标

```
读 wiki/{repo}/endpoint-flows.md，为每个 endpoint 产出一份测试案例清单，写成 wiki/{repo
```

- 步骤

```
1. 读 wiki/{repo}/endpoint-flows.md，拿到每个 endpoint 的 mermaid 调用链。
2. 对每个 endpoint，从图里逐项提取测试案例：
  - 正常路径：主流程走通，返回成功。
  - 每个分支：触发每个分支条件，验证走哪条路、得到哪个结果。
  - 每个下游调用：下游失败 / 超时 / 返回异常时，本服务怎么处理。
  - 每个落库点：数据写对没有；写失败时怎么处理。
  - 标"待确认"的节点：设计一条"固化现状"的测试，把当前实际行为记录下来，单列为最高优先级，等人确
3. 每个案例记下：覆盖哪条路径、给什么输入、期望什么输出。
4. 写成 wiki/{repo}/test-cases.md：
| endpoint | 覆盖路径 | 输入 | 期望输出 | 优先级 |
```

- 验证

```
读 wiki/{repo}/endpoint-flows.md，核对图里每个分支、每个下游调用、每个落库点都在 test-cas
```

- 注意

```
- 一条路径至少一个案例，分支不能只测"是"不测"否"。
- 下游失败这种异常路径最容易漏，别只写正常路径。
- "待确认"的节点不是跳过，而是用测试把现状固化下来，再标出来等人审：这个行为是本来就该这样，还是历
- 这一步只设计案例，写清楚"给什么、期望什么"，不写测试代码。写代码是下一步的事。
```

以及：

```
name: test-implement
description: 根据 wiki/{repo}/test-cases.md 的测试案例清单，在对应 repo 里实现测试代码。
```

- 目标

```
读 wiki/{repo}/test-cases.md，在 checkout/{repo} 里写出能跑、能覆盖清单上每条案例的测试代
```

- 步骤

```
1. 读 wiki/{repo}/test-cases.md，拿到案例清单。
2. 在 checkout/{repo} 里摸清测试现状：
  - 用什么测试框架（读构建文件 pom.xml / package.json / go.mod / Cargo.toml，或找已有测
  - 测试放哪个目录、命名规则是什么
  - 下游调用怎么 mock（找现有的 mock / stub 写法，照着用）
3. 按清单逐条写测试：
  - 正常路径和分支：构造输入，断言期望输出。
  - 下游调用：mock 掉下游，模拟成功、失败、超时、异常返回，断言本服务的处理。
  - 落库点：用测试数据库或 in-memory 替代，断言写对。
  - "待确认"的案例：写成探针，先按图上的猜测写期望，跑一遍看结果。
4. 跑测试，确保能编译、能执行。
5. 把结果写回 test-cases.md：哪些通过、哪些失败、失败的暴露了什么。
```

- 验证

```
跑测试，对照 test-cases.md 逐条核对：清单里每一条案例都有对应的测试代码，且能执行。缺一条回补。
```

- 注意

```
- 只加测试代码，不改任何生产代码。
- mock 写法照抄 repo 里已有的，别引入新的测试框架或依赖。
- "待确认"案例的测试失败不是 bug，是信息：它暴露了实际行为和图上猜测不符。把真实行为记下来，写回
- 测试要能独立跑、能重复跑，不依赖手工步骤或特定机器状态。
```

注意，我们这里只是给个例子。实际设计测试案例和实现测试代码时，需要考虑业务场景以及所用的测试框架，可能还需要补充其他的知识。

## 在 AGENTS.md 中列出

最后一步，是在 AGENTS.md 中列出我们支持的任务。一旦完成回归测试的编写，我们就可以修改 AGENTS.md，告诉用户这个 Workspace 能干什么。

这一步容易被忽略，但它恰恰是让 Workspace 真正“可用”的关键。AGENTS.md 是整个Workspace 的入口，写的是地图、约定、意图。前面几节建好了知识（wiki）、工作流（skills）、干活的地方（checkout），可如果入口里不说清楚“这里支持哪些任务”，那么一个人或一个 Agent 进来，看到一摞 skill，也不知道能干什么、该从哪个下手。

所以我们要在 AGENTS.md 里加一段，列出支持的任务，每个任务讲清三件事：怎么触发、走哪条 skill 链、产出什么。比如：

- 支持的任务

- 为遗留系统增加回归测试

```
触发：说"给 XX 服务加回归测试"，或"补一下 XX 的测试"
流程：implement-flow → test-case-design → test-implement
产出：wiki/{repo}/endpoint-flows.md、wiki/{repo}/test-cases.md，以及 repo 里的测试代码
```

有了这段，AGENTS.md 就从一张“目录说明”升级成了一份“能力清单”。用户想知道这个Workspace 能干什么，就看这段内容；Agent 接到任务，同样看这段内容，就知道该按哪条链走。

## 小结

- 知识提取是任务驱动的，不是一次囤够的：任务没发生就不知道会缺哪块知识，所以正确姿势是“遇缺即补”。spec/contract 给的是接口知识，回归测试要的却是行为知识——给一个确定的输入，系统该返回什么、发生什么。

- 用 implement-flow 把每个 endpoint 的行为画成 mermaid 调用链、存进知识库，是一种几乎无损的上下文压缩：保留“调了什么、查了什么、发了什么、怎么分叉”，丢掉实现细节，比让 LLM 每次重复读源代码省得多。这张图天然就是回归测试的提纲，图上每个分支、每个下游调用、每个落库点都是一条该测的路径。

- 回归测试的流程是两个 skill 串起来：test-case-design 把图变成测试案例清单，test-implement 把清单变成测试代码。写代码只加测试、不改生产，mock 照抄 repo 里现成的写法。

- “待确认”的节点用探针测试处理：跑挂了不是 bug，是信息，说明实际行为和图上猜测不符。需要把真实行为回写 endpoint-flows.md，让知识库被测试反向校准一次，而不是把断言偷偷改成能过。

- 最后把支持的任务写进 AGENTS.md（怎么触发、走哪条 skill 链、产出什么），入口就从“目录说明”升级成“能力清单”，完成从“搭骨架、补知识、做任务”到“能干什么一目了然”的闭环。
