# 12 | 前馈痴迷：Agent做完就交，从来没人检查

你好，我是徐昊，欢迎继续学习驾驭工程。

前面说过，前馈能够提高 Agent 在第一次尝试时就产生好结果的概率。不过一味只在前馈上面用功过度，也不是好现象，今天我们就来看看什么是前馈痴迷，还有它对应的重构手法。

## Bad Smell：前馈痴迷（Feedforward / Guides Obsession）

用大模型，最常遇到的场景就是大模型给出的结果跟我们的要求存在差异。我们已经知道有更好的办法能够帮助我们规范大模型的行为。比如，通过提取指令文件（Extract InstructionFile）对需求进行澄清。比如，在写周报这件事上：你每周都要写周报，你已经把需求提取成了指令文件（AGENTS.md）：周报的结构、风格要求、工作流程都写清楚了。

但是，大模型给出的结果与你的期待可能仍有一些差异。你的第一反应是什么？

大概率是往 AGENTS.md 里补充更详细的说明：“亮点要带数据”“语气要客观”“阻塞项要写责任人”等等。随着前馈控制逐渐增多，这又很容易会陷入指令文件腐化（Instruction File Rot）的陷阱。

但很少有人会换个思路。也就是与其继续补充要求，不如增加验证的环节，比如“自动检查：是否有至少 2 个亮点？亮点是否有数据？阻塞项是否有责任人？”。这就是坏味道前馈痴迷（Feedforward / Guides Obsession）。

所谓前馈痴迷，是指我们过度依赖前馈，遇到问题第一反应是加规则、加说明，而不是建立对应的反馈机制。正如我们在双层循环中讲到，反馈与前馈缺一不可。

前馈和反馈本质上是概率和证据的区别。前馈提高的是“做对的概率”，反馈提供的是“做对的证据”。指令写得再细，也只是让 Agent 更可能做对；只有检查才能证明它做对了。反馈太弱导致操控循环中无法形成有效的自我纠正，Agent 则会过于草率地结束任务。

## 为什么我们更习惯写前馈

为什么我们总是写前馈而不是反馈呢？根源在于一个更深的习惯：我们习惯从“怎么做”开始给出指令，而不善于描述“如何检查做完的结果”。

“亮点要带数据”和“检查亮点是否有数据”，一个是编写过程描述，一个是对结果检查描述。写过程描述容易：只需要一个模糊的期望，“带数据”就行了。写结果描述难：什么叫有数据？必须包含数字？百分比算吗？只有对比才算吗？要把“做完的结果”描述清楚，你必须先真正想明白这件事。

这个困难不是驾驭工程时代才出现的。在更早的管理学里就有印证。

比如，SMART 原则是设定目标的经典框架，它要求目标满足五个条件：S 具体（Specific）、M 可衡量（Measurable）、A 可实现（Achievable）、R 相关（Relevant）、T 有时限（Time-bound）。其中 M 可衡量以及 A 可实现，都是比较难写的条目。

再比如，KR（Objectives and Key Results，目标与关键结果）也一样，根据 Objective 来写Key Result 也是更困难的一步。

当然，这个到了程序员这边就更具体了，TDD（Test-Driven Development，测试驱动开发）写测试就比写代码困难。写代码只需要一个大概的思路，边写边调整；写测试却要求你在写任何实现之前，就精确描述“做完后应该表现出什么行为”：输入是什么、输出是什么、边界情况怎么处理。所以 TDD 推行了几十年，真正坚持下来的团队不多，因为它强迫你先把“做完的结果”想清楚。

写反馈控制和测试是同一回事，就是给 Agent 写测试，定义什么算做对。造成这个坏味道的是同一个习惯：不愿意面对“描述做完的结果”这个更难的认知任务。于是我们看到一个普遍的现象：指令文件越来越厚，反馈环节却总是相对薄弱。

## Solution：反馈优先

消除前馈痴迷的手法叫反馈优先（Feedback First），更完整的说法是：优先写反馈，而不是前馈。当你觉得需要给 Agent 加一条控制时，先写它的结果检查形式，而不是过程规则形式。

同一个意图，两种写法。“亮点必须有数据”是前馈形式，它告诉 Agent 该怎么做；“检查亮点是否有数据”是反馈形式，它告诉 Agent 交付前要检查什么。坏味道是我们习惯写前者，重构就是优先写后者。

为什么先写反馈而不是前馈？有三个理由。

第一，检查在操控循环的反馈环节，Agent 执行时一定会走到；规则在前馈环节，Agent 可能读了也不当回事。同样是“亮点要有数据”，写在检查步骤里，Agent 每次都会执行；写在规则里，它可能扫一眼就过去了。

第二，检查的结果是证据。检查通过，说明真的做到了；规则只是提高了做对的概率。前馈提高“做对的概率”，反馈提供“做对的证据”，我们在坏味道部分已经讲过这个区别。

第三，先写反馈会自然减少前馈的膨胀。同一个意图，写成检查之后就不用再写规则了。我们在工作流程里写了“自动检查：是否有至少 2 个亮点？亮点是否有数据？阻塞项是否有责任人？”，就没有必要再单独写“亮点要有数据”这类规则。这也是为什么指令文件腐化，根源之一就是只写前馈不写反馈。

你可能会问，写成检查是不是就要写脚本？不是。反馈检查不一定是脚本。能写成脚本的检查，比如字段是否填写、格式是否合规，写成脚本更可靠；需要语义判断的检查，比如亮点是否有数据、句子是否通顺，交给 Agent 判断即可。背单词技能里的判分，就是推断型反馈的正当用法。反馈检查的实现按检查的性质选，不是必须计算化。

## 什么时候该做这个重构

在我看来，这应该是默认最佳实践，而不是等到出问题才做的重构。任何时候你觉得自己需要给 Agent 加一条控制，都应该先问：这条控制的反馈形式是什么？可以优先先写检查，而不是先写规则。

原因在于前馈痴迷是本能，不是特例。只要开始写规则，就很容易一路写下去：加一条规则解决一个问题，下一个问题再补一条，直到指令文件膨胀。等到问题爆发再回头补反馈，已经积累了大量的前馈债。反过来说，从第一条控制开始就写反馈形式，成本几乎一样，却从一开始就建立了证据链。不要等到 Agent 基于过时的规则做出错误决策后才去修复，而应该从一开始就把反馈优先作为 Harness 的标配。

当然，如果你已经在问题里了，也有一些信号可以帮助你判断，你发现自己又在给指令文件加规则、加说明，而同类错误还在出现。这是最直接的信号：写前馈没解决问题，说明缺的是反馈。

## 如何重构

既然写反馈检查的难点在于“描述做完的结果”，而这是我们最不擅长的认知任务，那么重构的关键就是：让大模型帮我们完成这个翻译。

比如，我们可以盘点现有控制。把 AGENTS.md 里的规则列出来，区分哪些是前馈（要求Agent 怎么做）、哪些是反馈（要求 Agent 检查什么）。然后，让大模型把前馈改写成反馈。直接告诉 LLM：我有一份指令文件，里面都是对 Agent 的要求。请把每一条要求改写成对应的检查项，“必须 X”“检查 X 是否成立”。比如“亮点必须带数据”改写成“检查亮点部分是否包含数据”。

大模型擅长这个翻译，因为它已经理解了我们这一讲的核心：同一意图，可以有两种形式，而我们要的是检查形式。

当然这里有一个问题是，可能我们自己也没有想清楚要如何定义完成的状态。那么，我们可以用面试式追问澄清细节。有些规则一次改写不出来，因为“什么叫有数据”这类问题连你自己都没想清楚。这时候可以让大模型扮演一个苛刻的面试官，对每条前馈连续追问，直到细节被澄清。这里我们可以使用类似于 grill-me 这类现成的 skill，帮助我们完成对于验收条件的澄清。

最后，我们可以按检查性质，将能写成脚本的反馈写成脚本（字段完整性、格式校验），需要语义判断的保留为推断型检查，由 Agent 判断。不强制计算化，检查不一定是脚本。

整个重构过程，你真正要做的只是两件事：盘点出已有的前馈，然后让大模型帮助它们找到各自的反馈形式。剩下的事情，大模型会替你完成。

## 小结

- 前馈痴迷坏味道的本质：不是忘了检查，而是我们倾向于写前馈而不写反馈。遇到 Agent行为不对，默认动作是加规则，而不是建检查。根源是一个更深的习惯：我们习惯从“怎么做”开始给出指令，而不善于描述“做完的结果”。这个困难在管理学里早有印证：SMART 中M 和 A 最难写，OKR 中 Key Result 比 Objective 难写，TDD 中测试比代码难写。

- 前馈提高“做对的概率”，反馈提供“做对的证据”。只有前馈没有反馈，Agent 会过于草率地结束任务。

- 重构手法是反馈优先：先写反馈形式，而不是前馈形式。把规则改写成检查，“必须 X”“检查X 是否成立”。反馈检查不一定是脚本，需要语义判断的交给 Agent 即可。

- 这应该是默认最佳实践，而不是等到出问题才做的重构。重构时真正要做的只有两件事：盘点出已有的前馈，然后让大模型帮助它们找到各自的反馈形式。
